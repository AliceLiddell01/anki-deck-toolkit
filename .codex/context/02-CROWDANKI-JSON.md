# CrowdAnki JSON: карта формата

## Зачем нужен этот документ

CrowdAnki-экспорт может занимать мегабайты и десятки тысяч строк. Агенту не нужно перечитывать его целиком перед каждой задачей. Сначала используй эту карту, затем подтверждай нужные детали по фактическому файлу.

## Основные сущности

Типичный экспорт представляет корневую колоду `Deck` и вложенные колоды через `children`.

Практически важные ключи:

- `__type__` — тип сериализованной сущности, например `Deck`, `Note`, `NoteModel`, `DeckConfig`;
- `name` — имя колоды, модели или конфигурации;
- `children` — вложенные колоды;
- `notes` — заметки, принадлежащие конкретной колоде;
- `fields` — значения полей заметки в порядке, заданном её моделью;
- `guid` — стабильный идентификатор заметки Anki;
- `note_model_uuid` — связь заметки с `note_models`;
- `crowdanki_uuid` — идентичность сущности CrowdAnki;
- `deck_config_uuid` — связь колоды с `deck_configurations`;
- `note_models` — описание полей, CSS и шаблонов карточек;
- `deck_configurations` — настройки планировщика/колоды, включая FSRS-параметры, если они экспортированы;
- `media_files` — имена media-файлов, объявленных для поддерева этой колоды;
  объявления могут находиться в разных узлах `children`.

## Как разрешать поля заметки

Нельзя надёжно интерпретировать `notes[].fields[n]` только по номеру позиции.

Правильный путь:

```text
Note.note_model_uuid
→ NoteModel.crowdanki_uuid
→ NoteModel.flds
→ поле с соответствующим ord
→ Note.fields[ord]
```

Пример текущего состояния на сегодня: у японской словарной колоды в
`decks/output/<имя_экспорта>/` модель заметки `Слова` имеет шесть полей:

```text
0  Слово
1  Часть речи
2  Значение
3  Ударение
4  Пример
5  Похожие слова
```

Это навигационная карта сегодняшнего экспорта, а не контракт формата: имена полей
задаёт конкретная модель заметок, а toolkit работает с произвольным
CrowdAnki-экспортом. Имя каталога в `decks/output/` — тоже состояние на сегодня, а
не требование к раскладке. Перед любой правкой соответствие всё равно должно быть
подтверждено по самому JSON, а не взято из этого списка.

## Модель карточки

`note_models[].tmpls` содержит шаблоны карточек:

- `qfmt` — лицевая сторона;
- `afmt` — обратная сторона;
- `ord` — номер шаблона;
- `name` — имя шаблона.

`note_models[].css` содержит CSS модели. Изменение `fields` не должно случайно затрагивать `tmpls` или `css`.

## Media

`media_files` хранит имена файлов, а HTML внутри полей заметки может ссылаться на
них через конструкции вроде:

```html
[sound:word.mp3]
<img src="word.png">
```

JSON сам по себе не доказывает наличие бинарного media-файла в репозитории или
локальной коллекции Anki. Шаблоны `note_models[].tmpls[].qfmt/afmt` и CSS модели
также могут запрашивать media, поэтому поиск потребителей не ограничивается
полями заметок.

### Разрешённое размещение и миграция media

`create` по умолчанию запрещает ссылки на media в новых полях. Только точное
правило для сочетания UUID модели и имени поля может включить обработчик домена;
он допускает проверенную ссылку на canonical filename для своей `AssetIdentity`.
При `--apply` команда размещает проверенные байты в `media/` и добавляет
объявления `media_files`, необходимые соответствующему поддереву. В dry-run
файлы и экспорт не меняются.

`migrate-media` — единственное исключение для изменения ссылки в существующей
заметке. Владелец домена должен доказать точную пару `AssetIdentity` и legacy
filename. Команда инвентаризирует ссылки в полях заметок, `qfmt`, `afmt` и CSS;
непринадлежащая или статическая ссылка на старое имя блокирует миграцию. Для
объявлений `media_files` учитывается расположение по всему дереву `children`.
Только при явном `--apply` публикуется новый `deck.json`, размещается проверенный
канонический файл и после публикации удаляется соответствующий legacy-файл.
Ручная правка `deck.json` или файлов `media/` в обход этой проверки запрещена:
она не сохраняет доказательство семантики и согласованность объявлений.

## Deck config и FSRS

`deck_configurations` может содержать параметры новых карточек, повторений, lapses и FSRS. Эти настройки относятся к поведению планировщика и не должны изменяться при обычном редактировании словарной статьи.

Не путай:

- глобальную конфигурацию/preset;
- deck-level overrides вроде лимитов;
- содержимое заметок.

## Безопасная навигация по большому JSON

Рекомендуемый порядок разведки:

1. распарсить JSON и получить верхнеуровневые ключи;
2. вывести дерево `name` + количество `notes` + количество `children`;
3. получить список `note_models` и их `flds`;
4. получить список `deck_configurations`;
5. только после этого искать конкретные заметки или подколоды;
6. для массового анализа использовать скрипт, а не последовательное чтение десятков тысяч строк.

## Что сохранять при правке

По умолчанию сохраняй:

- UUID и GUID;
- дерево колод;
- порядок полей;
- неизвестные ключи;
- CSS и templates;
- deck config;
- существующее форматирование JSON.

Меняй только ту поверхность, которую требует задача.

## Добавление заметки

Новая заметка — это новый элемент в `notes` целевого узла, и адресуется она так
же, как существующие:

- `note_model_uuid` — общий `crowdanki_uuid` выбранной модели, а не её имя;
- `fields` — значения **в порядке `ord`** модели: `fields[i]` принадлежит полю,
  у которого `note_models[].flds[].ord == i`, независимо от порядка объявления;
- `guid` — уникальный идентификатор заметки. Именно по `guid` CrowdAnki
  сопоставляет заметку при импорте: заметка с новым `guid` создаётся, а заметка
  без своего `guid` в JSON не удаляется и не перезаписывается;
- `tags` — теги заметки;
- `__type__: "Note"` — тип узла.

Практические следствия, на которые опирается `tools/anki-repo create`:
новая заметка добавляется **в конец** `notes`; набор ключей не расширяется;
колода и модель адресуются идентичностями, а не именами; по умолчанию значения
новых полей не ссылаются на media. Только явно разрешённый обработчик может
использовать проверенный файл и материализовать его при `--apply`; произвольные
ссылки остаются запрещены. Схема полей берётся из фактического `flds` (см.
`tools/anki-repo models`), а не из памяти агента.

## Вывод заметки из обращения

Физического удаления заметок toolkit не делает. Причина в семантике импорта
CrowdAnki: заметка, отсутствующая в JSON, **не** считается удалённой, поэтому
«удаление» правкой JSON было бы ложью — после импорта заметка осталась бы в
коллекции со своим прошлым содержимым. Безопасная замена — тег вывода из
обращения: заметка остаётся на месте, остаётся адресуемой по `guid` и остаётся
полной; меняется только её `tags`. Удаляет заметку человек в Anki, когда это
действительно нужно.

## Каноническое форматирование

Экспорты в этом репозитории записаны в одной канонической форме:

- переводы строк только LF;
- отступ — 4 пробела;
- ключи объектов в алфавитном порядке;
- non-ASCII символы хранятся как есть, без `\u`-экранирования;
- файл не заканчивается переводом строки.

Этого списка недостаточно как проверки. `edit` сравнивает `deck.json` побайтово с
собственным рендером — `serde_json` с `PrettyFormatter` и отступом в 4 пробела
(`loader::CANONICAL_INDENT`) — и отвергает файл при любом расхождении байтов
(`reason: canonical_round_trip_mismatch`). Канонична ровно та форма, которую
выдаёт этот рендер, поэтому у списка есть следствия:

- числа записываются так, как их сериализует `serde_json`, а не так, как они были
  записаны в тексте: `1e3` → `1000.0`, `1e23` → `1e+23`;
- управляющие символы U+0000–U+001F экранируются короткими формами `\b`, `\f`,
  `\n`, `\r`, `\t`, остальные — как `\uXXXX` с шестнадцатеричными цифрами в
  нижнем регистре (`\u001f`); символы вне этого диапазона, например U+007F,
  остаются как есть;
- `"` и `\` экранируются как `\"` и `\\`.

Поэтому «выглядит канонично» не равно «канонично»: надёжная проверка — сравнение
с рендером, а не визуальный осмотр.

Команда `edit` в `tools/anki-repo` требует именно такой `deck.json` и отвергает
любую другую форму кодом `source_not_canonical`, а не нормализует файл молча.
Причина практическая: каноническая перезапись документа побайтово совпадает с
исходником везде, кроме изменённого значения, поэтому точечная правка не может
переписать остальной файл. Если `deck.json` оказался в другой форме, его
нормализация — отдельная задача с отдельным независимым diff, а не побочный эффект
правки содержимого.
