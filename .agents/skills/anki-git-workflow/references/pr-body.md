# Описание PR

Этот файл — владелец **содержательной структуры** PR body для
`anki-git-workflow`. Источник body, способ публикации, read-back, Draft/Ready,
merge и cleanup принадлежат `pr-lifecycle.md`.

## 1. Главный принцип

Пиши для человека, который не читал чат и видит только PR. Body должен быстро
отвечать на вопросы: зачем существует изменение, что именно изменилось, как это
проверено, в каком состоянии CI/review и какие ограничения остаются.

Заголовок и обычный текст — на русском; точные имена API, CLI, файлов, классов,
команд, кодов причин и CI jobs сохраняются.

Body строится по **фактическому состоянию** текущего work item. Не копируй
исходный prompt, transcript агента, полный журнал команд, временный roadmap или
старое состояние, которое уже не соответствует HEAD.

## 2. Обязательная структура содержательного PR

Любой **содержательный PR текущего work item** использует реальные
Markdown-заголовки второго уровня. Это относится не только к коду, tests,
config, workflow и repository skills, но и к документации и другим
отслеживаемым изменениям репозитория. Пользовательские колоды, ресурсы,
содержимое карточек, note models и media через Git не публикуются и в описании
PR не фигурируют:

```text
## Цель
## Область изменений
## Реализация
## Проверки
## CI
## Готовность
## Ограничения
```

Перед публикацией и после read-back запускай на полном Markdown body
`python3 .github/scripts/check_pr_body.py --body-file <путь-к-body.md>`.
GitHub Actions повторяет эту проверку на событиях PR. Не объявляй успешным
результат без проверки и не подменяй автоматически проверяемые заголовки
субъективной оценкой. Автоматизация проверяет структуру и непустоту разделов,
но не доказывает достоверность заявленных тестов и CI — эти факты сверяются
отдельно. Зависимые PR проверенных Renovate/Dependabot аккаунтов исключены
только при совпадении имени бота и префикса его ветки.

Не заменяй эту структуру одним сплошным текстом, подписями вида `Проверки:`
или единственным списком. Разделы должны быть визуально отделены именно
`##`-заголовками. Исключение — только действительно служебная mutation без
содержательного repository diff; обычная правка кода, документации или
конфигурации исключением не является.

### `## Цель`

1–3 плотных предложения:

- какую проблему или capability закрывает PR;
- почему изменение нужно;
- какое наблюдаемое состояние должно быть после merge.

### `## Область изменений`

Кратко фиксируй фактическую границу:

- основные подсистемы, owners и типы изменённых артефактов;
- repository/base/head branch;
- exact base SHA и текущий HEAD, когда они доступны и полезны для проверки;
- важный out-of-scope только если без него граница неочевидна.

Не превращай раздел в полный список файлов.

### `## Реализация`

Опиши существенные инженерные решения и их причины:

- владельца данных/поведения;
- изменённый flow или contract;
- важные failure/recovery semantics;
- сохранённые инварианты.

Пиши о результатах, а не о последовательности действий агента.

### `## Проверки`

Только фактически выполненные проверки и их результаты. Для каждой существенной
проверки должно быть понятно, что именно она подтверждает. Честно указывай
непройденную или недоступную проверку; не выдавай planned check за выполненный.

### `## CI`

Укажи состояние hosted checks относительно **текущего PR HEAD**:

- exact HEAD, если он нужен для исключения stale evidence;
- обязательные jobs/contexts и их состояние;
- `pending` / `NOT_RUN` / недоступность, если финального результата ещё нет.

Не называй зелёным CI от предыдущего HEAD.

### `## Готовность`

Кратко зафиксируй terminal state work item:

- реализация завершена или что ещё осталось;
- Draft/Ready;
- состояние обязательного review;
- merge не выполнен без отдельного разрешения пользователя.

### `## Ограничения`

Только реальные ограничения, риски, недоступные проверки или препятствия.
Если существенных ограничений нет, скажи это одной строкой вместо искусственного
списка.

## 3. Условные разделы

Добавляй отдельные `##`-разделы, когда они действительно применимы.

### `## Live acceptance`

Используй, когда выполнялся реальный runtime/browser/Anki/media acceptance,
который существенно сильнее статических tests. Опиши сценарий, наблюдаемый
результат и cleanup временных данных.

### `## Безопасность / проверка секретов`

Используй, когда задача затрагивает trust boundary, filesystem/network input,
secrets либо когда выполнялся отдельный security/secret scan.

### `## Миграция / откат`

Используй для migration, compatibility window, recovery/rollback или изменения
persistent/runtime contract, где это реально имеет смысл.

### `## Внешняя проверка`

Используй для внешнего reviewer, который не имеет собственного более точного
раздела.

### `## CodeRabbit review и disposition`

После запуска `anki-coderabbit-review` этот раздел **обязателен** и является
накопительным журналом именно содержательных результатов review, а не transcript
CLI.

Используй **одну таблицу** на весь CodeRabbit cycle:

```markdown
| Итерация / reviewed HEAD | Уровень | Путь | Влияние | Решение | Исправление |
| --- | --- | --- | --- | --- | --- |
| 1 · `<sha>` | major | `path/to/file` | <технический эффект> | confirmed | <что исправлено и каким commit опубликовано> |
```

Правила таблицы:

- после **каждой completed iteration** добавляй новые строки в эту же таблицу;
  предыдущие строки не удаляй и не переписывай ради красивого итога;
- первая колонка однозначно связывает строки с номером iteration и
  **reviewed HEAD**, то есть состоянием, которое действительно видел provider;
- на каждый provider finding сохраняй его фактический `severity`, путь,
  технический эффект, итоговый disposition и результат;
- допустимые disposition определяет `anki-coderabbit-review`; не превращай
  `false positive` или `stale/repeated` в якобы выполненный fix;
- если iteration действительно завершилась с `0 findings`, добавь одну
  summary-строку с `—` в `Уровень` и `Путь`, `clean` в `Решение` и
  укажи опубликованный marker commit в `Исправление`;
- если findings были, но все оказались false positive/stale, строки всё равно
  остаются в таблице с честным disposition;
- новый commit после fixes **не** выдаётся за reviewed HEAD той же iteration:
  следующая iteration проверяет уже новое опубликованное состояние;
- сырой reviewer output, prompts и длинные `codegenInstructions` в body не
  копируй.

CodeRabbit skill владеет тем, **когда** iteration завершена, как triage'ятся
findings и какие данные должны попасть в строки. Этот файл владеет тем, **как**
они представлены в PR body.

## 4. Плотность и читаемость

Обычно достаточно короткого абзаца или 2–6 содержательных пунктов на раздел.
Это ориентир, не квота. Для крупной архитектурной работы раздел может быть
длиннее, но стену текста разбивай по смыслу.

Предпочитай:

- короткие абзацы;
- списки для независимых фактов;
- таблицы только для действительно табличных данных;
- code spans для путей, команд, SHA и identifiers.

Не вставляй повтор одного и того же evidence в несколько разделов.

## 5. Актуализация body

Body — живое описание PR, а не текст только на момент создания.

При изменении фактов:

1. сначала обнови repository-local `.codex/local/pr/<task>/body.md`;
2. перечитай полный файл и проверь структуру этого документа;
3. опубликуй его способом из `pr-lifecycle.md`;
4. перечитай опубликованный PR и сравни полный body с локальным источником.

После CodeRabbit completed iteration актуализация cumulative disposition table и
успешный read-back являются частью завершения iteration: следующая iteration не
начинается, пока PR body не отражает предыдущую.
