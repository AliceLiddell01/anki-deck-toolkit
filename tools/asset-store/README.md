# Хранилище ресурсов и `kanji-assets`

**Русский** · [English](README.en.md) · [简体中文](README.zh-CN.md)

`asset-store` — общая библиотека Rust для ресурсов, которыми управляет программа.
Она отвечает за манифест, контрольные суммы, целостность и жизненный цикл.
Предметный CLI `kanji-assets` добавляет поиск статьи Yarxi, проверку изображения
кандзи и публикацию подтверждённых файлов в канонический корпус.

Инструмент не читает `decks/**/media/`, не меняет `media_files` и не копирует
изображения в колоды.

## Где лежат данные

CLI Kanji по умолчанию использует `.asset-store/kanji`. Следующий самостоятельный
домен хранится в `.asset-store/pitch-accent`; два публикуемых корпуса не делят
манифест или каталог `assets/`.

```text
.asset-store/                          # целиком игнорируется Git (/.asset-store/)
├── kanji/
│   ├── .owner.json                 # маркер владельца; в Git не публикуется
│   ├── manifest.json               # только действующие VERIFIED-записи
│   ├── assets/
│   │   ├── gif/漢.gif
│   │   └── png/饅.png
│   ├── .runtime/                   # кандидаты, карантин, наборы
│   ├── .journal/events.jsonl       # журнал операций; только дополнение
│   ├── .tmp/                       # подготовка и маркеры транзакций
│   └── .lock
└── pitch-accent/
    ├── .owner.json
    ├── manifest.json
    ├── assets/png/幽霊.png             # consumer_filename:幽霊.pitch.png
    ├── .runtime/
    ├── .journal/events.jsonl
    ├── .tmp/
    └── .lock
```

Корневой `.gitignore` исключает `/.asset-store/` и `/decks/` целиком:
whitelist-исключений внутри этих областей нет, поэтому
в Git не попадают ни `.owner.json`, ни `manifest.json`, ни байты ресурсов, ни
`.runtime/`, ни журнал операций. Отсутствие корпуса в чистом clone — нормальное
состояние, а не повод что-то публиковать.

Внутренний `storage_path` и имя файла для конечного потребителя — разные значения
манифеста. Например, `assets/gif/漢.gif` имеет `consumer_filename: "漢.gif"` и
попадает в `media/漢.gif`. `anki-repo` использует явное имя файла для потребителя
и не извлекает его из структуры хранилища ресурсов.

`.runtime/manifest.json` использует тот же `store_id`, что и основной манифест.
`verify_integrity` проверяет обе области. Записи `Pending` и `Quarantined` остаются
в `.runtime`; проверка только подтверждённых записей сверяет канонический корпус
и отсутствие пересечения идентичностей с `.runtime`. Отсутствующий корпус допустим.

## Политика домена и манифест

`AssetDomainPolicy` задаёт допустимые идентичности, путь канонического хранилища, имя
файла для потребителя, публикуемые форматы и ограничения размера.
`GenericDomainPolicy` сохраняет адресуемую по хешу структуру для непубликуемых
общих ресурсов. Предметные политики не принимают идентичности другого пространства имён:
`KanjiDomainPolicy` владеет `kanji`, `PitchAccentDomainPolicy` — `pitch_accent`.

Для миграции прежнего имени файла владелец домена отдельно доказывает его
соответствие идентичности через
`AssetDomainPolicy::proves_legacy_consumer_filename(identity, filename)`. По
умолчанию и для общего домена доказательств нет. Kanji допускает только точное
`<key>.gif` или `<key>.png`, pitch-accent — только точное `<key>.png`; во всех
случаях имя обязано быть безопасным именем файла без каталога. Эта проверка не использует
`legacy_location`: тот описывает старое расположение файла внутри манифеста, а не
имя, которое Anki видит в `media/`.

Kanji GIF и PNG физически разделены по `assets/gif/` и `assets/png/`, при этом
имя файла — точный символ и расширение. Для pitch-accent ключом служит точная
словоформа (`surface`), а не чтение (`reading`): PNG хранится в
`assets/png/<surface>.png`, а потребитель получает имя `<surface>.pitch.png`.
Например, запись для `飴` хранится как `assets/png/飴.png` и передаётся Anki под
именем `飴.pitch.png`; имя медиа кандзи `飴.png` остаётся отдельным. Чтение и
положительный идентификатор словарной записи JPDB входят в метаданные и
доказательства.

Хранилище владеет **каноническим** именем потребителя, но не переписывает ссылки в
уже существующих заметках. Если под прежним именем `<surface>.png` в экспорте
осталась старая ссылка на изображение тонового акцента, её переводит на каноническое имя команда
`anki-repo migrate-media` (`tools/anki-repo/README.md`); хранилище ресурсов при этом
остаётся источником проверенных байтов и не переименовывает собственные файлы.
Сопоставление считает хирагану и катакану эквивалентными при сравнении чтения,
но требует совпадения точной пары `surface` и `reading` с одной из форм выбранной
словарной записи. В `evidence` сохраняется исходное чтение JPDB. Одного
декодирования PNG недостаточно для статуса `VERIFIED`:
`PitchAccentImageValidator` проверяет пару словоформы и
чтения, фактическую страницу словарной записи с тем же ID, наличие
хотя бы одного графика и доказательства тёмной темы.

В `evidence` сохраняются прямоугольники каждого графика в координатах области
просмотра и документа, их геометрическое объединение и `capture_rect`. Снимок
одного графика совпадает с прямоугольником DOM-узла, а снимок нескольких
охватывает их геометрическое объединение. Естественные промежутки между графиками
сохраняются; внешняя рамка или отступ не добавляются. Проверка допускает расхождение
размеров PNG не более чем на 3 пикселя из-за округления границ нативного
CDP-параметра `clip`. Доказательства тёмной темы связывают настройку цветовой схемы
браузера, класс документа и вычисленный стиль фона с пикселями PNG. Для фона
достаточно хотя бы одного
пикселя, у которого разница каждого RGB-канала с наблюдённым цветом не превышает
8; как минимум у восьми пикселей графика хотя бы один канал должен отличаться от
него более чем на 16. Каждый пиксель PNG должен иметь `alpha=255`. Эти проверки
просматривают весь снимок, поэтому искусственный тёмный край не нужен.
Происхождение браузера обязательно. Текущий контракт отрисовки и доказательств
проверяет валидатор v5; доказательства версии 4 не наследуют его доверие, а
неполные доказательства получают `UNCERTAIN`.

Версия схемы манифеста — `5`. Помимо SHA-256, размера, формата, состояния,
происхождения и смыслового решения, каждая запись хранит `consumer_filename`, а
всё хранилище — `domain_id`. Автоматическая запись `ValidationRecord` и
необязательная `HumanAttestation` привязаны к точной идентичности и SHA. Для
pitch-accent решение человека `Approve` не заменяет автоматическую запись
`ValidationRecord`: для тех же байтов нужна запись со статусом `VERIFIED` и
ожидаемыми `validator.id`/`validator.version` для `PitchAccentImageValidator` v5.
Подтверждение человека не делает пригодными старые или неполные доказательства,
`REJECTED` либо `CORRUPT`. Это
требование относится к pitch-accent и не меняет существующие правила обработки
`Approve` для Kanji. Новый SHA не наследует решения предыдущих байтов. Замена
записи требует операции `compare-and-swap` по ожидаемому старому SHA.

Схемы v3/v4 и прежнее плоское расположение Kanji читаются. Изменяющее открытие
выполняет версионную миграцию под исключительной блокировкой: сохраняет старые
байты жёсткой ссылкой, сверяет SHA-256, атомарно обновляет манифест и удаляет
прежние плоские ссылки. Маркер транзакции в `.tmp/` позволяет завершить или
откатить прерванный переход.
`ValidationRecord`, `HumanAttestation` и SHA неизменившихся байтов сохраняются;
повторное получение не требуется. После фиксации старого и нового канонического пути
одновременно не остаётся. CLI JSON сообщает `store.layout_migrated_on_open`.

`AssetStore::read_verified` остаётся доступным для чтения совместимым API с
`KanjiDomainPolicy`. Потребители других доменов используют
`read_verified_with_policy`; этот API также читает файлы прежних схем v3/v4
через прежнее сопоставление и возвращает явный `consumer_filename`, но не пишет
манифест, не создаёт служебные файлы состояния и блокировки, не меняет расположение и не запускает
восстановление. Миграция выполняется только при изменяющем открытии. Проверяются
точные байты, контрольная сумма, размер, формат, идентификатор валидатора и решение человека.

Общая среда выполнения пакетов владеет безопасной файловой механикой
`.runtime/batches/<batch-id>`: `NOFOLLOW`, блокировкой, ревизией/CAS, атомарной
записью состояния, ограниченным чтением и файлами содержимого, адресуемыми по SHA. Он не
знает о `KanjiBatch`, `KanjiMetrics`, данных Yarxi или HTML-отчёте; эти правила
остаются в предметных адаптерах. Тестовое состояние в обычном текстовом формате
проверяет повторное открытие и чтение блока данных без правил изображений или кандзи.

Общие сеансы Chromium, поиск исполняемого файла, сведения о запуске, метрики CDP
и сетевая техническая телеметрия находятся в `browser_runtime.rs`. Yarxi сохраняет
собственные селекторы, адреса URL, правила TLS, фильтры, резервный источник, тёмную тему
и геометрию снимка. Общая среда выполнения позволяет задать отдельный коэффициент
масштабирования `3.0`. Провайдер JPDB использует изолированную сессию; отдельный
`pitch-assets` владеет обработкой пакетов и публикацией подтверждённых PNG.
Интеграция с `anki-repo` остаётся отдельной возможностью.

Пользовательские области не публикуются через Git ни целиком, ни частично:
корневой `.gitignore` исключает `/.asset-store/` и `/decks/` целиком, и исключений
внутри них нет. Проверить правила можно настоящим
`git check-ignore` с помощью отдельного регрессионного скрипта — он копирует
корневой `.gitignore` во временный репозиторий, доказывает игнорирование всех
путей внутри двух областей (включая `.owner.json`, `manifest.json`,
`assets/**`, `.runtime/**`, `.journal/events.jsonl`, каталоги группировки прежней
раскладки и вложенные каталоги) и
проверяет, что после `git add -A` в индексе не остаётся ни одного такого пути:

```bash
bash tools/asset-store/tests/gitignore_regression.sh
```

`kanji-corpus-gate` и `pitch-corpus-gate` проверяют, можно ли публиковать корпус
соответствующего домена. Они отклоняют неподтверждённые состояния жизненного цикла,
доказательства от устаревшего валидатора, старую плоскую структуру, пути с
суффиксом SHA, потерянные файлы и незарегистрированные канонические пути.

Проверить корпуса кандзи и тонового акцента из корня рабочего пространства можно командами, которые
только читают данные:

```bash
cargo run --quiet --locked -p asset-store --bin kanji-corpus-gate
cargo run --quiet --locked -p asset-store --bin pitch-corpus-gate
```

Проверка завершается с ненулевым кодом, если запись не имеет действующего
`VERIFIED`, используется неподдерживаемая структура или неверная политика домена,
доказательства валидатора устарели, найдены потерянные байты или повреждено
состояние среды выполнения. Проверка ничего не меняет и не считает временные данные частью
канонического корпуса.

## Журнал операций

Журнал объясняет, как хранилище пришло к текущему состоянию. Он лежит в
`<store-root>/.journal/events.jsonl` рядом с `manifest.json`, но вне
`.runtime/batches/**`, поэтому переживает удаление локального состояния одного
пакета. Файл только дополняется: одна строка — один JSON-объект (NDJSON), и
каталог журнала игнорируется Git вместе с остальным `.asset-store/`.

Журнал — история переходов, а не второй манифест. Источником истины о текущем
`VERIFIED`-корпусе остаётся `manifest.json`; журнал лишь объясняет, как это
состояние получилось, и позволяет найти изменение, зафиксированное в манифесте,
но не закрытое событием результата. В журнале нет токенов, cookie, CDP-дампов,
HTML-отчётов и изображений: только идентичность, операция, SHA-256, состояние
жизненного цикла, ревизия манифеста, техническая причина и снимок счётчиков
`baseline`.

Пример реальной строки:

```json
{"schema_version":1,"seq":2,"event_id":"c3dca04948e2cecdef3dda4b70c81f8b2268a2844707d64b197ba7e64bd5a96e","event_key":"a143ed00d781b3439a0f0688125f45e9d34f08aa9e75ac91e5e30c67746e4b68","recorded_at":"2026-10-15T22:08:27.113Z","domain":"kanji","namespace":"kanji","identity":"漢","operation":"candidate_written","outcome":"completed","intent_id":"441132dfc6eff6e5cd75a3d55566026727b115bedf2724beb252106874778a14","manifest_revision":1,"previous_sha256":null,"new_sha256":"693d949d8c3fdc7fd4ace7c340b5f177a9f0c5be7bafee8bc93a7d88b7523d75","previous_lifecycle":null,"new_lifecycle":"pending","verified":false,"run_id":null,"batch_id":null,"provenance":"local_import:han.gif","reason":null,"snapshot":null}
```

Полное чтение ограничено 256 МиБ. Выше этого предела `journal list`,
`journal check` и `journal reconcile` завершаются `journal_too_large` (код 4), а
запись продолжает работать: дописыванию нужны только ключи уже записанных
событий и номер последнего, поэтому файл обходится потоково. Ротации нет — чтобы
снова читать историю целиком, `.journal/events.jsonl` архивируют вручную;
источником истины остаётся `manifest.json`, поэтому архив истории не влияет на
корпус.

| Поле | Значение |
| --- | --- |
| `schema_version` | версия формата события (`1`) |
| `seq` | номер события в файле, строго `+1` |
| `event_id` | идентификатор события; на него ссылается `intent_id` |
| `event_key` | ключ идемпотентности по полям события; проверяется при `journal check`. Для совместимости принимается и ключ схемы 1, созданный до включения `intent_id` в хеш |
| `recorded_at` | время записи в RFC 3339 UTC |
| `domain`, `namespace`, `identity` | владелец записи; у событий уровня хранилища `identity` = `*` |
| `operation` | `candidate_written`, `verified_published`, `verified_reused`, `trust_granted`, `trust_revoked`, `revalidated`, `quarantined`, `removed`, `recovered`, `layout_migrated`, `baseline` |
| `outcome` | `pending`, `completed`, `refused`, `recovered`, `aborted`, `unknown` |
| `intent_id` | `event_id` интента, который закрывает это событие |
| `manifest_revision` | суммарная ревизия канонического и `.runtime` манифестов |
| `previous_sha256`, `new_sha256`, `previous_lifecycle`, `new_lifecycle` | фактическое состояние записи до и после события |
| `verified` | `true` — запись `verified` после события; `false` — не `verified` или удалена; `null` — событие не относится к одной записи |
| `run_id`, `batch_id` | контекст запуска, если он задан |
| `provenance` | `source_kind:source_name` без пути |
| `reason` | техническая причина отказа, восстановления или удаления |
| `snapshot` | снимок `assets`/`verified`/`pending`/`quarantined` у `baseline` |

### Двухфазная запись

Изменение состояния обрамляется двумя событиями. Перед изменением пишется интент
(`outcome: pending`) с текущим состоянием в `previous_*` и ожидаемым в `new_*`;
его `event_id` становится `intent_id`. После успешного `save_manifest` пишется
закрывающее событие с тем же `intent_id`, `outcome: completed` и фактическими
`manifest_revision`, `new_sha256`, `new_lifecycle`, `verified`. Штатный отказ до
фиксации закрывает интент событием `outcome: refused` с `reason`, поэтому
висящих интентов обычная работа не оставляет.

Запись идёт только из точек, которые уже удерживают эксклюзивную блокировку
store, и только когда запись действительно изменилась. Ни один worker пакета и
ни один параллельный путь пакетной обработки в журнал не пишет, поэтому
многоворкерное получение не замедляется.

Событие `verified_reused` пишется только тогда, когда повторное использование уже
доверенного ресурса с тем же SHA действительно состоялось. Из того, что в
манифесте уже лежит `VERIFIED`-запись, событие `verified_published` не выводится.

### Сверка

Если процесс умер между `save_manifest` и закрывающим событием, интент остаётся
висящим. `journal reconcile` под блокировкой читает журнал и сравнивает
незакрытые интенты с фактическим состоянием канонического и `.runtime`
манифестов. Проверка допускает восстановление корректного открытого интента,
но отказывает с `manifest_corrupt` без записи, если история содержит неверные
ссылки, битые строки или оборванный хвост, несовпадающие
`domain`/`namespace`/`identity`/`operation`, нарушенный порядок, повторное
закрытие или неверный производный `event_key`:

- фактическое состояние совпало с ожидаемым `new_*` → `outcome: recovered`;
- совпало с прежним `previous_*` → `outcome: aborted`;
- ни то, ни другое → `outcome: unknown` с объясняющим `reason`.

Решение валидатора и доверие человека меняют только `validation` и
`human_attestation`, а `sha256` и жизненный цикл оставляют прежними: по манифесту
такой переход неотличим от отсутствия перехода. Поэтому интент такого перехода
закрывается как `unknown` с причиной «манифест не различает применённое и
неприменённое изменение», а отказ тела перехода не выдаётся за `refused` — исход
считается неизвестным, а не угаданным.

Сверка идемпотентна: повторный вызов не дописывает событий.

### Команды

Оба CLI читают журнал своего store, который задаётся общим `--store`.

```bash
# События по возрастанию seq; --limit оставляет последние N.
kanji-assets --store .asset-store/kanji journal list --limit 20
pitch-assets --store .asset-store/pitch-accent journal list \
  --identity 幽霊 --operation verified_published

# Целостность: строгая нумерация seq, уникальность event_id, корректность event_key;
# результат ссылается на предшествующий Pending той же области и операции;
# также проверяются допустимые однофазные события, оборванный хвост,
# битые строки и ревизия не выше фактической.
# Код возврата 3, если найдена проблема; открытые интенты перечисляются.
# Журнал больше предела полного чтения — journal_too_large (код 4).
kanji-assets --store .asset-store/kanji journal check

# Сверка незакрытых интентов; печатает дописанные события.
kanji-assets --store .asset-store/kanji journal reconcile

# Одно событие baseline со снимком текущего состояния; повтор отклоняется.
kanji-assets --store .asset-store/kanji journal baseline
```

`journal baseline` пишет ровно одно событие `operation: baseline` с
`identity: "*"`, фактической ревизией и снимком
`assets`/`verified`/`pending`/`quarantined`. Оно обозначает начало доверенной
истории и не переписывается: повторная запись завершается отказом.

## Получение изображений тонового акцента из JPDB

`JpdbPitchProvider` работает со страницами поиска и словарными страницами JPDB.
URL поиска задаёт `q` через API `URL` и явно устанавливает `lang=english`. После
перехода провайдер принимает страницу `/search` или допустимое перенаправление
сразу на `/vocabulary/<id>/...`. Во втором случае перед получением графика отдельно
проверяются ID записи, соответствие запросу и необязательный явный выбор. Любой
другой маршрут или значение `origin` приводит к отказу. Поиск проверяет связанную
пару написания и чтения среди наблюдённых форм, включая подтверждённые
альтернативные формы. При неоднозначности провайдер не выбирает первый или наиболее
ранжированный результат: он возвращает `ambiguous_vocabulary` и кандидатов с
ID словарной записи, формами и чтениями, частями речи, значениями и фактической
словарной ссылкой. Потребитель может передать явный `JpdbPitchSelection` через
`JpdbPitchRequest`. Провайдер выполняет новый поиск и принимает выбор, только если
ID, `surface` и необязательный `reading` из ссылки совпадают с одним из найденных
кандидатов. Параметры запроса и фрагмент ссылки не входят в идентичность. Допустимая
ссылка использует HTTPS-узел `jpdb.io`, стандартный порт и точный путь из трёх или
четырёх непустых сегментов `/vocabulary/<positive-id>/<surface>[/<reading>]`;
косая черта в конце пути не разрешена. Провайдер не доверяет произвольному URL или ID,
использует фактический `href` результата и не строит словарную ссылку из входных
строк. Без явного выбора неоднозначный запрос остаётся неоднозначным, а
`vocabulary_not_found` отделён от технической ошибки.

Для подтверждённой словарной страницы `no_pitch_accent_on_source` возвращается,
только если распознана ожидаемая структура и в ней нет секции `Pitch accent`.
Неизвестный или пустой набор графиков в DOM, сетевой или JS-сбой,
неподтверждённая тёмная тема и некорректный снимок остаются техническими
ошибками. Перед фиксацией отсутствия провайдер дожидается завершения критических
запросов к странице и повторно проверяет её структуру; произвольная пауза сама
по себе не считается доказательством. Сбой выполнения или декодирования ответа
`page.evaluate()` сохраняется как `browser_evaluation` с активной стадией;
противоречивые данные DOM остаются `page_contract`, а превышение срока ожидания —
`timeout`.

Все найденные узлы графиков выбранной словарной записи снимаются одним снимком
через CDP при масштабе страницы `1.0` и DSF `3.0`; PNG после захвата не
масштабируется, не обрезается и не перекодируется. Координаты узлов сохраняются
относительно области просмотра и документа с учётом `scrollX`/`scrollY`. Область
снимка совпадает с прямоугольником DOM-узла для одного графика либо охватывает
геометрическое объединение узлов для нескольких;
техническое расхождение ограничено округлением границ параметра `clip` захвата
CDP. В `evidence` входят прямоугольники графиков, итоговая область снимка,
размеры области просмотра и страницы, масштабы, размеры PNG и сведения о фоне.
Валидатор проверяет геометрию и размеры PNG с допуском до 3 пикселей при
округлении границ `clip`, настройку цветовой схемы браузера и класс `dark-mode`,
а также пиксели фона и
графика. Все пиксели PNG должны иметь `alpha=255`. Валидатор не распознаёт сам
рисунок ударения. Естественные промежутки между графиками сохраняются; внешняя
рамка не добавляется.

Каждый исход получения содержит исходные байты и `PitchAccentDomainMetadata`,
пригодные для `PitchAccentImageValidator`. `JpdbPitchProvider::acquire_requests`
запускает отдельную сессию для набора запросов;
`acquire_requests_in_session` принимает сессию вызывающего кода. В обоих случаях
запросы обрабатываются по очереди, но для каждого выполняется новый поиск.
Обычная ошибка одного элемента не останавливает пакет. Если наблюдатель CDP
теряет данные и сессию больше нельзя считать надёжной, отчёт содержит исходы
только уже начатых элементов и отдельный `session_failure`. Незапущенный хвост
не получает синтетических исходов и остаётся доступен для следующего запуска.

Для ручной приёмки используйте внешний JSON-план. Для каждого элемента обязательно
задайте `expected_outcome` одним из точных значений:
`acquired`, `no_pitch_accent_on_source`, `ambiguous_vocabulary` или
`vocabulary_not_found`. Дополнительно разрешены поля:

- `expected_vocabulary_id` и `min_graph_count` только для `acquired`;
- `expected_candidate_ids` только для `ambiguous_vocabulary`; значения должны
  точно совпасть с набором ID фактических кандидатов без учёта порядка;
- `selection` только для `acquired`. В нём обязательны `vocabulary_id` и
  `detail_url`; ID должен совпасть с `expected_vocabulary_id`, а ссылка должна
  соответствовать описанному выше маршруту JPDB с тем же ID.

До создания отчёта и запуска браузера программа проверяет запрос, идентичность домена
и имя для потребителя, числовые ограничения, повторы запроса и ссылку выбора.
Краевые пробелы в `surface` и `reading` обрезаются при поиске, а исходные значения
плана сохраняются в отчёте для диагностики. Повтор словоформы и чтения допустим
для обычного неоднозначного запроса и отдельного явного выбора; точный повтор
одной пары запроса и выбора отклоняется. После поиска провайдер повторно сверяет
выбор с фактически найденными кандидатами.

Синтетический пример показывает поля плана. Для реального прогона замените ID и
`detail_url` в `selection` на значения из `evidence` выбранного кандидата:

```json
{
  "items": [
    {
      "surface": "合成語",
      "reading": "ごうせいご",
      "expected_outcome": "acquired",
      "expected_vocabulary_id": 42,
      "min_graph_count": 1
    },
    { "surface": "別の語", "expected_outcome": "no_pitch_accent_on_source" },
    {
      "surface": "重複語",
      "expected_outcome": "ambiguous_vocabulary",
      "expected_candidate_ids": [101, 102]
    },
    {
      "surface": "重複語",
      "expected_outcome": "acquired",
      "expected_vocabulary_id": 101,
      "selection": {
        "vocabulary_id": 101,
        "detail_url": "https://jpdb.io/vocabulary/101/重複語/ちょうふくご"
      }
    },
    { "surface": "欠落語", "expected_outcome": "vocabulary_not_found" }
  ]
}
```

Запуск из корня рабочего пространства:

```bash
cargo run --locked -p asset-store --bin jpdb_pitch_acceptance -- \
  --plan ../jpdb-pitch-plan.json
```

Отчёт и доказательства каждого прогона сохраняются в одном проверенном ZIP;
распакованный каталог отчёта не оставляется. По умолчанию ZIP записывается в
`<std::env::temp_dir()>/anki-decks-evidence/jpdb_pitch_acceptance-run-<32 lowercase hexadecimal digits>.zip`.
`--output <ZIP>` задаёт путь к новому ZIP-файлу с расширением `.zip`; относительный
путь считается от текущего каталога. Родительский каталог должен существовать,
файл — ещё не существовать, путь должен находиться вне рабочей копии и временного дерева.
Для просмотра распакуйте ZIP: HTML находится в
`reports/index.html`, JSON — в `reports/evidence.json`, полученные изображения —
в `reports/images/`. stdout завершает публикацию блоком `LIVE EVIDENCE ZIP` с
абсолютным `Path`, `SHA-256` и `Size` в байтах. ZIP может содержать частичный
отчёт и при ошибке проверки плана; итоговый статус и доступные результаты
записываются в `evidence`.

Отчёт для каждого элемента содержит ожидаемый и фактический исход, результат
сравнения, сведения о кандидатах, фактические ID словарных записей и ссылки,
формы и чтения, доказательства тёмной темы, геометрию графиков и снимка, DSF,
размеры PNG, SHA-256 и решение основного валидатора. Исход `acquired` считается
успешным, только если статус валидатора — `VERIFIED` и соблюдены ограничения
плана. Ожидаемые неоднозначность, отсутствие записи и отсутствие изображения тонового акцента могут
быть успешными исходами; неожиданно не найденная словарная запись означает
ошибку прогона. Отсутствующий результат провайдера и локальная ошибка обработки
также считаются несовпадением. Ошибка одного элемента не удаляет уже собранные
данные. Исходные байты результата `acquired` сохраняются без преобразования;
PNG с неверной сигнатурой или ошибкой декодирования доступен как `.bin` и не
показывается как изображение. Инструмент не меняет каноническое хранилище,
пользовательские медиафайлы или `decks/**`; ZIP остаётся локальным артефактом.

## `pitch-assets`: канонический корпус и обработка пакетов

CLI получает изображения тонового акцента, хранит состояние пакетов и публикует подтверждённые
PNG в `.asset-store/pitch-accent`. Он не читает экспорты CrowdAnki и не знает
имён моделей карточек или полей заметки. Без `--store` используется хранилище
изображений тонового акцента в текущей рабочей копии. `--output json` возвращает машиночитаемый
результат с версией схемы.

Коды завершения `pitch-assets`:

- `0` — успешная команда; для `ensure`, `batch run` и `batch resume` все
  элементы пакета разрешены.
- `3` — пакет после получения остаётся нерешённым (`needs_review`), либо
  `AssetError` сообщает об ошибке ввода, конфликте идентичности или недопустимом
  переходе. Для различения используйте `outcome`, `blockers` и `error` в JSON.
- `4` — отказ `AssetError` из-за границ, целостности, владения хранилищем,
  отсутствующего хранилища или неподдерживаемой схемы.
- `5` — ошибка I/O или валидатора (`AssetError::exit_code()`), а также ошибка
  записи stdout, кроме `BrokenPipe`; при `BrokenPipe` сохраняется код результата.

Ошибки разбора аргументов CLI возвращают `2` до выполнения команды. Для ошибок
хранилища код берётся из `AssetError::exit_code()`, а не из статуса пакета.

```bash
# Просмотр и проверка корпуса без сетевого получения.
cargo run --locked -p asset-store --bin pitch-assets -- corpus list
cargo run --locked -p asset-store --bin pitch-assets -- corpus check

# Одно получение или пакет по строгому JSON-плану.
cargo run --locked -p asset-store --bin pitch-assets -- ensure \
  --surface '幽霊' --reading 'ゆうれい'
cargo run --locked -p asset-store --bin pitch-assets -- batch start \
  --plan ./pitch-plan.json
cargo run --locked -p asset-store --bin pitch-assets -- batch run \
  --batch-id my-pitch-batch --workers 4

# Состояние, отчёт проверки и продолжение после решения.
cargo run --locked -p asset-store --bin pitch-assets -- batch status \
  --batch-id my-pitch-batch
cargo run --locked -p asset-store --bin pitch-assets -- batch review \
  --batch-id my-pitch-batch
cargo run --locked -p asset-store --bin pitch-assets -- batch resume \
  --batch-id my-pitch-batch --workers 4

# Явный выбор кандидата, адресный или пакетный повтор, отказ для точного SHA.
cargo run --locked -p asset-store --bin pitch-assets -- batch select \
  --batch-id my-pitch-batch --surface '重複語' --vocabulary-id 101 \
  --detail-url 'https://jpdb.io/vocabulary/101/重複語/ちょうふくご'
cargo run --locked -p asset-store --bin pitch-assets -- batch retry \
  --batch-id my-pitch-batch --surface '幽霊' --reason 'повтор после временной ошибки'
cargo run --locked -p asset-store --bin pitch-assets -- batch retry-technical \
  --batch-id my-pitch-batch --reason 'пакетный повтор временных ошибок'
cargo run --locked -p asset-store --bin pitch-assets -- batch reacquire \
  --batch-id my-pitch-batch --surface '幽霊' --reason 'явное обновление записи'
cargo run --locked -p asset-store --bin pitch-assets -- batch reject \
  --batch-id my-pitch-batch --surface '幽霊' \
  --sha256 "$CANDIDATE_SHA256" --reason 'визуально отклонён'
```

Внешний JSON-план `PitchPlan` имеет `schema_version: 1`; неизвестные поля и
версии отклоняются. Сохранённое состояние пакета имеет отдельную версию схемы 2.
Старое состояние схемы 1 завершается ошибкой: CLI не пытается восстановить по
истории текущую попытку кандидата или исходный план. Каждый элемент плана
содержит точную `surface`, необязательный `reading` и необязательный `selection`
с `vocabulary_id` и `detail_url`. Одинаковые запросы схлопываются, а несовместимые
запросы с одинаковым `surface` приводят к `identity_conflict` до запуска браузера.

При создании пакета CLI нормализует запросы и сохраняет их как неизменяемый
`original_plan` вместе с SHA-256. Команды выбора, повтора и повторного получения
меняют активный запрос элемента, но не исходный план. Повторное использование того
же `batch_id` разрешено только при совпадении исходного плана и его дайджеста.
Для выбора из `ambiguous_vocabulary` укажите точные ID и `detail_url` кандидата из
отчёта проверки. Следующий `batch run` выполняет новый поиск и повторно
подтверждает выбранную запись в JPDB.

```json
{
  "schema_version": 1,
  "items": [
    { "surface": "幽霊", "reading": "ゆうれい" },
    {
      "surface": "重複語",
      "reading": "ちょうふくご",
      "selection": {
        "vocabulary_id": 101,
        "detail_url": "https://jpdb.io/vocabulary/101/重複語/ちょうふくご"
      }
    }
  ]
}
```

`batch status` проверяет целостность хранилища и сверяет сохранённый пакет со
свежим полным снимком канонических записей. Эта команда не запускает браузер и
не обращается к сети; при изменении данных хранилища она сохраняет обновлённое
состояние пакета. В JSON поле `changed` равно `true`, если команда изменила
сохранённые данные канонического корпуса или пакета, включая новое состояние,
байты кандидата и файл `review.html`. Создание служебной блокировки или пустых
каталогов не считается изменением данных. В остальных
случаях `changed` равно `false`.

Состояние пакета хранит типизированные исходы провайдера, историю попыток,
неоднозначности, решения валидатора и намерения публикации. Текущий кандидат
связан с точным номером попытки, её поколением и SHA-256 содержимого. Поэтому
одинаковый SHA в разных попытках не смешивает их запросы и доказательства. Сами
байты дедуплицируются по SHA и сохраняются до публикации в
`.runtime/batches/<id>/candidates/`. На время браузерного запроса блокировка
среды выполнения снимается; после него CLI сверяет поколение и ревизию элемента и
отбрасывает устаревший результат. После перезапуска `resume` повторно проверяет
кандидата текущим валидатором и может продолжить публикацию без повторного JPDB
запроса.

`batch run` и `batch resume` принимают `--workers` от `1` до `4`; значение по
умолчанию — `4`. Некорректное значение отклоняется до начала получения. Каждый
исполнитель владеет отдельными `BrowserSession`, `Page`, CDP-соединением, профилем
браузера, `TMPDIR` и временным `TempWorkspace`. Исполнители параллельно получают
назначенные записи, поэтому результаты могут завершаться не в порядке исходного
плана. Значение `4` выбрано для повышения пропускной способности по результатам
сравнительного прогона. Если `jpdb.io` отвечает HTTP 429, уменьшите `--workers`,
чтобы снизить число одновременных запросов.

Изменения состояния сериализует один координатор. Он назначает каждому
исполнителю не более одной записи, а при получении результата проверяет
назначение и сохранённый `token`/`CAS`: поколение, запрос и ревизию элемента. При
совпадении координатор надёжно сохраняет результат и байты кандидата в отдельной
контрольной точке, после чего выполняет готовую публикацию и назначает исполнителю
следующую запись. Результат с устаревшим `token` отбрасывается и не заменяет новое
состояние. Контрольная точка сохраняется сразу, независимо от порядка завершения:
пакетом владеет набор уже сохранённых результатов, а не непрерывный префикс
плана. Невыдаваемая очередь и прерванные до сохранения контрольной точки элементы
остаются `pending`. При `resume` очередь строится заново после сверки состояния и
включает текущие элементы `pending`; сохранённый кандидат можно повторно проверить
или опубликовать без нового запроса к JPDB.

При старте `batch run` и `batch resume` очистка осиротевших временных деревьев
выполняется явно, даже если браузер не понадобится. Исполнители создают свои
временные деревья только при запуске браузера.

Во время получения прогресс сразу отправляется в `stderr`: человекочитаемыми
строками в обычном режиме и JSON Lines при `--output json`. Каждое событие
прогресса JSONL имеет `schema_version: 1`, `operation: "batch_run"`, `event`, `batch_id`,
`elapsed_ms`, `run_completed`, `run_total` и `batch_total`. Поля `workers` и
`in_flight` добавлены к схеме и присутствуют в каждом событии: `workers` —
заданная степень параллелизма, `in_flight` — число назначенных, но ещё не
завершённых записей. `run_total` — число записей в состоянии `pending` после
сверки пакета в начале запуска, `batch_total` — полный размер пакета.
`run_completed` увеличивается только после надёжного сохранения контрольной
точки; отброшенный устаревший результат счётчик не увеличивает.

В зависимости от события дополнительно передаются `identity`, `worker`,
`worker_session`, `session`, `next_session`, `attempt`, `recovery`, `outcome` и
`reason`. Нумерация `worker` начинается с `1`; `worker_session` — локальный номер
сессии браузера у исполнителя, также начиная с `1`. Номера `session` и
`next_session` уникальны в пределах запуска и общие для всех исполнителей.
События: `run_started`, `item_started`, `retry_started`, `heartbeat`,
`item_checkpointed`, `item_discarded_stale`, `item_requeued`,
`browser_session_started`, `browser_session_ended`, `browser_session_recovered`,
`browser_session_rotated`, `worker_recovery_exhausted`, `run_stopped` и
`run_finished`. `attempt` — номер попытки по сохранённой истории; `retry_started`
появляется при повторной попытке. `recovery` — длина текущей серии сбоев сессии
у этого исполнителя, начиная с `1`; поле присутствует только в событиях, которые
относятся к восстановлению сессии. Прогресс получения тонового акцента не содержит полей раундов. Для
`ensure` поле `operation` имеет значение `ensure`. При `--output json` прогресс
остаётся в `stderr` как JSON Lines, а `stdout` содержит один итоговый JSON-ответ
команды.

Обработчик паники процесса выдаёт отдельное JSONL-событие `panic` с полями
`schema_version: 1`, `event` и `message`; в нём нет `operation`, `batch_id` и
счётчиков прогресса. Сообщение фиксировано и не раскрывает содержимое паники или стек.

Каждый исполнитель независимо меняет свою сессию браузера перед следующей
записью при достижении любого лимита: 64 завершённых запроса или 20 минут с
момента запуска сессии. Уже начатый запрос не обрывается ради смены сессии и
ограничен тайм-аутом провайдера в 90 секунд.

Сбой сессии браузера остаётся локальным для исполнителя. Восстановимым считается
сбой запуска или настройки сессии, а также отчёт, в котором не больше одного
результата и присутствует отказ сессии. Исполнитель закрывает испорченную сессию,
проверяет доказанность её очистки и открывает новую; остальные исполнители
продолжают получать записи, поэтому локальная проблема браузера не останавливает
выдачу задач всему запуску.

Если отчёт не содержит результата, назначенная запись возвращается в конец
очереди: она не получает попытку, не меняет поколение и не превращается в
синтетический `technical_failure`. Если результат есть, он сохраняется ровно
одной контрольной точкой, после чего сессия меняется, а элемент больше не
переполучается. Серия сбоев считается подряд и сбрасывается полученным
результатом; если тот же отчёт сообщает и об отказе сессии, он становится первым
сбоем новой серии. Плановая смена сессии по лимиту и `Ctrl+C` в неё не входят. После
трёх подряд сбоев исполнитель выводится из пула: он завершает работу, его канал
задач закрывается, а запуск продолжается остальными исполнителями. Если очередь
всё ещё не пуста, `batch run` завершается ошибкой с причиной
`session_recovery_exhausted`, а неразобранные элементы остаются `pending` без
синтетических ошибок и попыток; их можно продолжить через `batch resume`.

Сбои, которые нельзя исправить сменой сессии, остаются отказом всего запуска:
отчёт с более чем одним результатом либо без результата и без отказа сессии
(`invalid_provider_report`), неподтверждённая очистка испорченной сессии
(`browser_cleanup_failed`), ошибка паники исполнителя, закрытый канал задач и
ошибка контрольной точки, `CAS` или хранилища. Локальное восстановление сессии
не скрывает их и не заменяет их исход.

При `Ctrl+C` координатор останавливает выдачу новых записей и посылает сигнал
активным запросам. Результат, завершившийся одновременно с сигналом, сохраняется,
если исполнитель уже его получил: координатор проверяет `CAS` и надёжно сохраняет
контрольную точку. Все активные сессии закрываются, а исполнители дожидаются
завершения и очистки своих временных каталогов. Запись без принятой контрольной
точки и невыданный хвост остаются `pending` без фиктивного исхода или попытки.
Следующий `batch resume` сверяет сохранённое состояние, продолжает с текущего
набора `pending` и сохраняет уже достигнутые контрольные точки.

Публикация читает метаданные и `evidence` только из указанной попытки и требует её
текущий `VERIFIED` результат от `PitchAccentImageValidator` v5. Перед записью
`AssetStore::ingest_verified` повторно проверяет байты и сверяет ожидаемый SHA
предыдущей записи операцией `compare-and-swap`. Публикуемая запись хранится как
`assets/png/<surface>.png`, а имя для потребителя — `<surface>.pitch.png`. Если
свежая сверка хранилища подтверждает существующую каноническую запись, проверенную
текущей версией валидатора, пакет может использовать её без нового сетевого получения.

Явный `reacquire` начинает новое поколение и фиксирует SHA текущей записи
хранилища как основу `compare-and-swap`. Если SHA владельца меняется после
фиксации этого основания, свежая сверка `batch status` покажет конфликт
`refresh_owner_drift` и заблокирует публикацию старого кандидата. `batch reacquire`
с обязательным `--reason` архивирует конфликтное намерение публикации, принимает
актуальное состояние владельца как новое CAS-основание, начинает следующее
поколение и снимает ссылку на старую попытку, поэтому она не будет опубликована.
Если повторное получение даёт тот же SHA,
метаданные и `evidence` обновляются только после повторной проверки байтов
валидатором v5 и при совпадении CAS с тем же SHA записи хранилища. В публикацию
попадают метаданные точной текущей попытки. Визуальный отказ привязан к SHA
конкретных байтов; другие SHA не наследуют его. `retry` разрешён для повторяемых
технических ошибок и не сбрасывает
соседние завершённые элементы. После сверки владелец может подтвердить запись
(`ExistingVerified`), хотя последний исход пакета остаётся устранимой технической
ошибкой. В этом случае адресный `retry` разрешён: он снимает отметку `ExistingVerified`,
начинает новое поколение и фиксирует текущий SHA владельца как CAS-основание.
Пакетный `batch retry-technical` с обязательным `--reason` применяет к каждому
элементу тот же критерий, что и адресный `retry`, и переводит в новое поколение
все текущие устранимые технические сбои пакета. Неустранимые технические сбои,
опубликованные элементы, элементы с незавершённым намерением публикации,
неоднозначные исходы, отсутствие тонового акцента, ненайденные и конфликтные
элементы, а также элементы в состоянии `pending` не меняются. Операция применяется
целиком или не применяется вовсе, а повторный запуск после успешного применения
не выбирает ничего. Если при
сверке владельца не возникло других сохранённых изменений, команда сообщает
`changed: false`; иначе `changed` отражает и эти изменения. В машиночитаемом ответе
выбранные идентичности
перечислены в `retried_identities` в порядке пакета; при пустом выборе поле
отсутствует. `no_pitch_accent_on_source` завершает только
текущий пакет, не создавая пустую запись или постоянный кэш отсутствия;
`vocabulary_not_found` остаётся отдельным нерешённым исходом.

`batch review` сохраняет `review.html` в игнорируемом каталоге `.runtime` пакета.
Отчёт показывает полученные и канонические PNG, словоформу и чтение, словарную
ссылку JPDB, число графиков, SHA-256, размер, статус валидатора и доказательства
источника и отрисовки. При неоднозначности он перечисляет всех кандидатов, а
отсутствие изображения тонового акцента, ненайденную словарную запись и техническую ошибку показывает
как типизированные исходы без фиктивных изображений. Строки экранируются;
HTML не меняет состояние пакета и не является источником истины. Решения
задаются адресными командами `select`, `reject`, `retry` и `reacquire`; ручного
способа опубликовать байты без текущей автоматической проверки нет.

### Очистка завершённых пакетов

Каждый `ensure` создаёт новый каталог с автоматически сгенерированным ID и не
принимает `--batch-id`. Для `batch start` ID можно указать явно; без `--batch-id`
он также генерируется автоматически. Каталоги сохраняются в `.runtime/batches/`.
Автоматической очистки нет: история, кандидатные байты
и отчёты накапливаются, в том числе при повторном использовании готового ресурса.
Перед ручной очисткой проверьте пакет через `batch status` и сохраните нужный
отчёт или историю вне хранилища. Завершите все процессы CLI, использующие это
хранилище, затем удалите только каталог выбранного завершённого пакета
`.runtime/batches/<batch_id>/`. Не удаляйте пакеты, которые нужны для `review`,
`retry`, `resume` или `reacquire`. Удаление пакета лишает этих возможностей и истории,
но не удаляет опубликованные записи канонического корпуса; каталог `assets/`
и манифест хранилища при такой очистке не затрагиваются.

## Получение с Yarxi

`ensure` открывает отдельную сессию Chromium без графического интерфейса и работает с фактическим
динамическим интерфейсом `https://www.yarxi.su/`. Поиск ограничен контейнером
поиска иероглифов, его полем «Чтение» и кнопкой «Найти». После открытия вкладки
«Информация» провайдер требует точную кодовую точку Unicode запрошенного символа;
несоответствующая статья отвергается. Номер статьи и метаданные источника входят
в сведения о происхождении изображения.

Обычный `ensure` сохраняет исходный приоритет основного `img.kakijun-gif` и
читает байты GIF через общий слой ресурсов браузера. Запасной вариант разрешён
только после доказанного отсутствия GIF: вкладка и область с изображением готовы,
точный Unicode подтверждён, относящиеся к странице запросы завершились без сетевых
ошибок, ошибок HTTP и JavaScript, DOM стабилен две секунды и элемент GIF отсутствует.
Запрос GIF в ожидании или с ошибкой загрузки, тайм-аут, незавершённая картинка,
ошибка сети или JavaScript дают ошибку получения;
эти состояния никогда не считаются `gif_absent`.

Обычный `ensure` использует `AcquisitionTarget::PreferredSource`: сначала
загружает основной GIF. К изображению `.font-sample` можно перейти только после
подтверждённого отсутствия GIF. Если у крайней слева допустимой плитки есть
подходящий исходный PNG, провайдер читает его байты; если изображение нарисовано
шрифтом, провайдер снимает сам элемент плитки. Явная цель
`AcquisitionTarget::RenderedFontSamplePng` запрашивает PNG после отрисовки даже
при наличии GIF; обычный `ensure` сохраняет приоритет GIF.

При подтверждённом отсутствии GIF провайдер выбирает крайнюю слева видимую
допустимую плитку `.font-sample`; классы `stroke-order` исключаются. Если у
плитки есть допустимый исходный PNG, стандартный запасной вариант читает его
байты. Если нужный образец отрисован текстом, провайдер устанавливает
воспроизводимую тёмную схему страницы: `prefers-color-scheme: dark` и
`data-theme="dark"` на корневом элементе Yarxi. На уровне страницы `#app` получает
цвет из текущей палитры тёмной темы,
поскольку его обычное CSS-правило задаёт светлый текст независимо от темы. Сам
`.font-sample` провайдер не перекрашивает и не перестраивает. Он снимает только
DOM-элемент плитки, сохраняя фон, рамку, отступы и отрисованный глиф; снимок всей
страницы не используется. В сведения о происхождении включены выбранная плитка,
прямоугольник CSS, вычисленные цвета, параметры шрифта, область просмотра,
масштаб устройства и фактические размеры PNG.

Правая ссылка `kakijun.jp` не читается как изображение и запрещена как источник.
Для разрешённых запасных изображений `blob:`/`data:` байты читаются в контексте
браузера. Перед семантической проверкой сверяются сигнатуры GIF/PNG; затем
декодер проверяет полный файл, размеры, непустую область рисунка и поток кадров
GIF. Плитка после отрисовки в браузере остаётся в исходном масштабе; фактические
размеры, область просмотра и масштаб устройства сохраняются в сведениях о происхождении.

### Ручная приёмка тёмных PNG

`yarxi_dark_acceptance` — ручное средство приёмочной проверки настоящих
PNG-изображений после отрисовки и HTML-просмотра результата. Оно получает символы
из внешнего JSON-плана; число элементов и групп не фиксировано. План должен
содержать непустой `items`, где у каждого элемента есть уникальный `character`,
который тип `KanjiCharacter` принимает как поддерживаемый скаляр Unicode из блоков Han/CJK.
Поле `group` необязательное
и должно быть непустым, если задано. Поля
`unicode_codepoint`, `yarxi_article_number` и `frequency_index` необязательны.
Провайдер всегда сверяет точный код Unicode символа со статьёй Yarxi; заданный
`unicode_codepoint` тоже должен совпадать с символом. Если заданы номер статьи
или индекс частотности, они сверяются с данными `evidence` Yarxi.

Например, план можно сохранить вне рабочей копии:

```json
{
  "items": [
    {
      "character": "漢",
      "group": "пример",
      "unicode_codepoint": "U+6F22",
      "yarxi_article_number": 123,
      "frequency_index": 45
    },
    { "character": "字" }
  ]
}
```

Запуск из корня рабочего пространства:

```bash
cargo run --locked -p asset-store --bin yarxi_dark_acceptance -- \
  --plan ../yarxi-plan.json
```

Для Yarxi по умолчанию разрешён переход по строго проверенной странице
предупреждения TLS. Параметр `--allow-insecure-tls=false` запрещает это исключение
и требует валидный сертификат.
Отчёт и доказательства каждого прогона сохраняются в одном проверенном ZIP;
распакованный каталог отчёта не остаётся. По умолчанию ZIP записывается в
`<std::env::temp_dir()>/anki-decks-evidence/yarxi_dark_acceptance-run-<32 lowercase hexadecimal digits>.zip`.
`--output <ZIP>` задаёт путь к новому ZIP-файлу с расширением `.zip`; относительный
путь считается от текущего каталога. Родительский каталог должен существовать,
файл — ещё не существовать, путь должен находиться вне рабочей копии и временного дерева.
HTML находится в `reports/index.html`, JSON — в
`reports/evidence.json`, изображения кандидатов — в `reports/images/`.
stdout завершает публикацию блоком `LIVE EVIDENCE ZIP` с абсолютным `Path`,
`SHA-256` и `Size` в байтах.
При ошибке ZIP может содержать доступные частичные результаты и сведения об
ошибке. Архивирование не добавляет кандидаты в хранилище ресурсов и не публикует их.
План и ZIP приёмочного прогона остаются локальными и не коммитятся. До отдельной публикации
владелец репозитория вручную просматривает реальные изображения, даже если
автоматическая семантическая проверка вернула `VERIFIED`.

Провайдер обрабатывает параллельные запросы отдельными исполнителями браузера;
каждый создаёт изолированный профиль браузера и `TMPDIR` внутри собственного
временного `TempWorkspace`. Для запуска нужен Chrome/Chromium; путь можно явно
задать через `CHROME_BIN` или `CHROMIUM_BIN`.
Также проверяются `PATH` и каталог кэша Playwright. Профиль браузера, файлы
cookie и состояние сессии не включаются в ZIP с подтверждающими материалами.

#### Ручная проверка ротации сеанса браузера и возобновления пакета кандзи

Для приёмочной проверки ротации в настоящем пакете кандзи можно явно собрать
`kanji-assets` с функцией Cargo `session-rotation-acceptance`. Только в этой
сборке для `batch run` доступен флаг `--acceptance-rotate-after-items N`; в
обычной сборке флага нет. Положительное `N` задаёт число элементов, результат
которых должен быть сохранён событием `item_checkpointed` в одном сеансе
браузера до плановой смены. После порога оставшаяся очередь продолжается в
новом сеансе. Порог считается заново для каждого сеанса и не меняет состав
пакета, попытки, поколения, контрольные точки или правила возобновления.

Эта функция Cargo нужна только для ускоренной приёмки. Обычные значения
остаются неизменными: не более 20 минут на сеанс браузера, 90 секунд на
элемент, 900 мс между элементами и до двух попыток получения. Без флага ранняя
ротация не включается; в обычной сборке `kanji-assets` остаётся только штатное
поведение.

Пример из корня рабочего пространства: используйте небольшой набор из трёх
символов, дождитесь `item_checkpointed`, затем `browser_session_rotated` и
`item_started` следующего элемента и нажмите `Ctrl+C`. Команды после остановки
проверяют состояние и продолжают тот же пакет с тем же ID и временным
хранилищем:

```bash
STORE="$(mktemp -d)"
BATCH_ID=yarxi-rotation-check

cargo run --locked --features session-rotation-acceptance -p asset-store --bin kanji-assets -- \
  --store "$STORE" batch start --batch-id "$BATCH_ID" 漢 字 語

cargo run --locked --features session-rotation-acceptance -p asset-store --bin kanji-assets -- \
  --store "$STORE" batch run --batch-id "$BATCH_ID" --rounds 1 \
  --acceptance-rotate-after-items 1

cargo run --locked --features session-rotation-acceptance -p asset-store --bin kanji-assets -- \
  --store "$STORE" batch status --batch-id "$BATCH_ID"

cargo run --locked --features session-rotation-acceptance -p asset-store --bin kanji-assets -- \
  --store "$STORE" batch run --batch-id "$BATCH_ID" --rounds 1 \
  --acceptance-rotate-after-items 1
```

В `status` проверьте, что уже сохранённый результат на месте; повторный
`batch run` продолжает незавершённые элементы того же пакета. Приёмочный флаг
управляет только моментом смены сеанса браузера и не меняет семантику пакета.

### Временное дерево и ZIP приёмочных сценариев

Обе приёмочные программы используют общий `EvidenceRun` и `TempWorkspace`.
По умолчанию временные данные прогона хранятся в приватном каталоге
`/tmp/anki-decks-<uid>/run-<32 lowercase hex>` с правами `0700`. Переменная
`ASSET_STORE_TEMP_ROOT` задаёт альтернативный абсолютный существующий корень без
symlink; тогда каталоги создаются под `<ASSET_STORE_TEMP_ROOT>/anki-decks-<uid>` и
начальная GC проверяет только этот корень, а не `/tmp`. Результат GC (включая
ошибку) кэшируется по значению абсолютного пути на время процесса, чтобы пул
обработчиков не повторял обход при каждом создании рабочего дерева.
Неявные API `cleanup_orphans`, `plan_orphans`, `cleanup_legacy_orphans` и `snapshot`,
а также начальная уборка пакетов pitch-accent используют этот же выбранный корень.
API с суффиксом `_under` проверяют только явно переданный корень. Отчёт `GcReport`
содержит `root`, включая пустой результат; настоящие ошибки отдельных деревьев
не кэшируются как успешная начальная уборка. `EvidenceRun` закрепляет выбранный
корень до завершения: `startup_gc`, `final_gc` и снимки состояния относятся к нему.
Текущие деревья находятся в пространстве имён UID, а `legacy` проверяет только
строго распознанные прежние имена непосредственно в том же корне.
Альтернативный корень применим к рабочим CLI и средам с ограниченным `/tmp`;
относительный `TMPDIR` также позволяет использовать длинный абсолютный путь к
корню без превышения предела Unix-сокета Chromium. Значение `TMPDIR` передаётся
браузеру без подмены байтов; значение вне UTF-8 отвергается
ошибкой `browser_tmpdir_invalid` до запуска браузера с очисткой созданного профиля.
Относительное значение
`ASSET_STORE_TEMP_ROOT` приводит к `InvalidInput`. Пространство имён разделено по
текущему UID. Каталог содержит маркер
`.anki-decks-owner.json` (поля `schema`, `repository`, `tool`, PID, время создания, `run_id`
и назначение). Новые маркеры схемы 2 дополнительно содержат `boot_id` и
`process_start_ticks` и публикуются атомарно. Старые маркеры схемы 1 остаются
читаемыми и очищаются только после прежнего TTL в 24 часа. При необходимости
профиль браузера создаётся как отдельный подкаталог рабочего пространства.
Профиль `browser-profile-<32 lowercase hex>` и временный
каталог Chromium `t<3 lowercase hex>` — соседние приватные каталоги (`0700`) одного
`BrowserProfile`. Короткое имя временного каталога сохраняет путь сокета Unix Chromium короче
ограничения `sockaddr_un.sun_path`. При запуске только дочерний процесс Chromium
получает `TMPDIR=<run>/t<3 lowercase hex>` через `BrowserConfig`; окружение
процесса `asset-store` и командная оболочка пользователя не меняется. Относительный
`TMPDIR` используется только если заданный `ASSET_STORE_TEMP_ROOT` после канонизации
совпадает с текущим каталогом процесса `asset-store`; в остальных случаях значение
остаётся абсолютным. Относительный `TMPDIR` проверяется относительно
`/proc/<pid>/cwd` самого процесса Chromium.
Перед удалением профиль
проверяется по соответствующему рабочему пространству: если командная строка,
`TMPDIR` или дескриптор процесса Chromium того же UID всё ещё ссылаются на запуск,
очистка отказывает и оставляет дерево на месте. Сначала завершаются браузер и
обработчик CDP, затем удаляются профиль и временный каталог браузера, и только
после этого закрывается рабочее пространство запуска. Оно закрывается явно после
сборки подтверждающих материалов; при обычном выходе `Drop` выполняет очистку по
возможности. Ошибки очистки содержат `stage`, стабильный
`code`, `path_category` и очищенное сообщение без абсолютного пути. ZIP создаётся
отдельно и сохраняется после удаления временного рабочего пространства. Для
артефакта обязательны `summary.md`, `manifest.sha256`,
`raw-evidence/events.jsonl`, `raw-evidence/technical-failures.json`,
`runtime/report-snapshot.json`, `timeline.jsonl`, `commands.json`, `checks.json`,
`fault-injection.json`, `metadata.json`, `hygiene.json`, `stdout/acceptance.txt`,
`stderr/acceptance.txt`, `logs/diagnostic.jsonl` и `reports/index.html`; каждый
остальной включённый файл покрыт SHA-256 в `manifest.sha256`. Архив проверяется
по обязательным записям, безопасным уникальным путям и полному совпадению SHA-256
с манифестом до публикации; существующий ZIP не перезаписывается. Если они созданы,
в архив также входят `reports/evidence.json`, `reports/images/*` и фактические
выводы под `stdout/` и `stderr/` для `git`, `rustc`, `cargo` и проверки
временной файловой системы. Архив собирается только из разрешённых каталогов отчёта,
телеметрии и журналов: исходный план, `store`, маркер владельца, профиль браузера,
файлы cookie и данные сеанса не включаются. JSON-подтверждения и диагностические
события очищаются от известных секретных полей; из URL удаляются параметры запроса и фрагмент.
`reports/index.html` — HTML-просмотр результата, а не сырой DOM страницы.

При создании `TempWorkspace` запускается GC каталогов-сирот с маркером владельца.
Для схемы 2 точная идентичность `(boot_id, PID, process_start_ticks)` позволяет
распознать работающего владельца, пережившую перезагрузку систему, отсутствующий PID
или повторное использование PID. Доказанно мёртвый владелец с маркером схемы 2
снимает барьер возраста; схема 1 по-прежнему требует TTL не менее 24 часов. Приёмочная программа
также сохраняет результаты начальной и итоговой очистки деревьев с маркером и
старых каталогов. Очистка деревьев с маркером рассматривает только
`<temp-root>/anki-decks-<uid>/run-<32 lowercase hex>` с приватным каталогом
и действительным маркером проекта и инструмента. `temp-root` равен `/tmp` по
умолчанию и `ASSET_STORE_TEMP_ROOT` при его задании. GC требует совпадения
`run_id`, UID и проверки ссылок процессов на дерево. Для схемы 2 несовпадающий
`boot_id`, отсутствующий PID или другой `process_start_ticks` доказывают смерть
исходного владельца; совпавшая идентичность означает, что владелец работает. Для схемы 1
сохраняется проверка PID и TTL. Проверки
выполняются относительно открытых дескрипторов каталогов с `NOFOLLOW`; чужой
UID, небезопасные права, граница точки монтирования, неизвестная символическая ссылка или специальный
файл, работающий владелец, будущая временная отметка и любой сомнительный маркер
или ошибка чтения идентичности процесса приводят к пропуску, а не к удалению.
Перед удалением осиротевшего дерева схемы 2 сборщик проверяет процессы того же
UID по `cwd`, открытым fd и `--user-data-dir`; для Chromium также проверяется
`TMPDIR`. Проверка повторяется
перед удалением после обхода дерева. Собственные fd, которые GC держит для
безопасного обхода, исключаются, но cwd и окружение текущего процесса проверяются.
Для схемы 1 прежняя проверка Chromium выполняется при наличии файлов браузера.
Проверка `TMPDIR` разрешает существующие предки и символические ссылки, затем
обычные имена отсутствующего остатка. Доказанно отсутствующий путь вне дерева
не блокирует независимые каталоги. Ссылка внутрь дерева, отказ доступа,
оборванная символическая ссылка или `..` после отсутствующего предка сохраняют
дерево. Для абсолютного `TMPDIR` не требуется чтение `cwd`; относительный путь
требует доказанного рабочего каталога процесса. Исчезновение процесса проверяется
по записи PID в `/proc`, отдельно от ошибки чтения одного источника.

Если нужные сведения о процессах недоступны, дерево пропускается. Сборщик распознаёт
только созданные формы Chromium внутри подтверждённого осиротевшего запуска:
профильные `SingletonCookie`, `SingletonLock`, `SingletonSocket`, каталог
`org.chromium.Chromium.<6 буквенно-цифровых символов>`, его символическую ссылку
на cookie-файл и сокет, а также обычные файлы
`.org.chromium.Chromium.<6 буквенно-цифровых символов>` в собственном временном
каталоге браузера. Символические ссылки не обходятся; каталог, граница fd, тип объекта, UID и граница точки монтирования
проверяются до удаления. Глобальные объекты `/tmp/org.chromium.*` и
`/tmp/.org.chromium.*` не являются целью очистки.
Начальный `snapshot` снимается до начальной очистки; итоговый — после удаления
текущего рабочего пространства и завершающей сборки мусора. Результаты очистки и
факт удаления рабочего пространства записываются в `hygiene.json`.

Очистка старых каталогов вызывается приёмочной программой при старте и перед
публикацией итогового ZIP через `cleanup_legacy_orphans(min_age)`. Она удаляет
только старые каталоги с подтверждёнными формами имён:
`anki-manifest-<метка-из-списка>-<pid>-ThreadId(<id>)`,
`asset-store-pitch-cli-<pid>-<sequence>`,
`asset-store-pitch-batch-<pid>-<sequence>`,
`jpdb-live-acceptance-<pid>-<timestamp>`,
`yarxi-live-acceptance-<pid>-<timestamp>` и `kanji-<32 lowercase hex>`. Для
TTL старых каталогов не может быть меньше 24 часов; если имя содержит PID,
живой процесс блокирует удаление. Также проверяются UID, отсутствие прав на
запись для группы и остальных пользователей, отсутствие символических ссылок,
границ точек монтирования и специальных файлов; неподтверждённые или сомнительные
деревья пропускаются. `snapshot()` только измеряет известные временные деревья и
не удаляет их. Оба GC работают только со своими распознанными префиксами; они не
обходят произвольные каталоги в системной временной папке.

### Сертификат Yarxi

Сейчас Chrome может показать `ERR_CERT_AUTHORITY_INVALID` для Yarxi. По умолчанию
разрешён только переход по ссылке «Перейти на сайт» на странице предупреждения
Chrome для исходного URL с точным именем узла
`www.yarxi.su`, при точном коде `ERR_CERT_AUTHORITY_INVALID` без учёта регистра
и наличии ссылки перехода. Глобальный
`--ignore-certificate-errors` и отключение TLS-проверки в процессе не включаются.
Область исключения ограничена Yarxi; `--allow-insecure-tls=false` требует валидный
сертификат. Другое имя узла, TLS-ошибка или форма URL по-прежнему приводят к
завершению запуска.

## Семантический валидатор и контрольный прогон

`KanjiImageValidator` анализирует пиксели PNG/GIF, а не имя файла, URL, текст DOM
или сведения о происхождении. PNG декодируется целиком. `GifDecoder::into_frames()` выдаёт
композитные кадры с учётом правил замещения предыдущих кадров GIF; модуль проверки
проверяет все кадры и берёт кадр с наибольшей площадью объекта на переднем плане.

`KanjiImageValidator` и адаптер пакетной обработки кандзи ограничивают изображения 8 МиБ.
Общая среда выполнения пакетов задаёт верхний предел 64 МиБ для состояния и
файлов содержимого, а предметный адаптер может установить меньший предел.
При одобрении человеком используется лимит текущей политики домена, а при его
отсутствии — 8 МиБ. При таком решении
читается не более выбранного предела плюс один байт, чтобы обнаружить превышение
без неограниченного выделения памяти, затем проверяется целостность и полностью
декодируется изображение.

Основной каталог эталонов построен из выпуска KanjiVG `r20250816`, коммит
`bd13ffbcc9d85cb86ae98bbbf001d9069220b901`. Исходные SVG, адресуемые по кодовым
точкам Unicode, нормализованы в 64×64 бинарные маски; каталог содержит 6 430 символов и включён
как сжатый `src/data/kanjivg-r20250816.maskdb.zlib` с SHA-256
`5581e65d5a681cdf8e441be04c1cea5f6ec61342ce8830ed083ba417d83a88ff`. KanjiVG
распространяется под CC BY-SA 3.0. Сведения об авторстве, версия выпуска и SHA-256
исходного архива зафиксированы рядом со сгенерированными данными в
`src/data/kanjivg-ATTRIBUTION.txt`.

Для тёмной плитки добавлен дополнительный пиксельный эталон из Noto Serif JP — того
шрифта, который Yarxi реально использует в `.font-sample`. Зафиксированный TTF
имеет SHA-256
`e6cffcd5cae6a298ddfd17173b42d64888913976b2d7053024a9ecf0cf5d3fe8`. Из него
генерируются 6 428 нормализованных масок в
`src/data/yarxi-noto-serif-jp-r1.maskdb.zlib` с SHA-256
`ea6231b13f23ed16705839b8c3e911f89fea67b91b6b315f3f562f75c7b0531c`; исходный
TTF не включён в репозиторий. Его происхождение и исходная лицензия описаны в
`src/data/yarxi-noto-serif-jp-ATTRIBUTION.txt`.

Валидатор сначала оценивает фон по угловым участкам растра, выбирает полярность
по контрасту, удаляет связанные компоненты рамки у края и строит маску глифа на
переднем плане. Построители эталонов и рабочий валидатор используют общую функцию
`kanji_mask::normalize_binary_mask`: она обрезает растр по непустой области
переднего плана, вписывает его в область 56×56 и центрирует в маске 64×64. Каждый
выходной пиксель выбирает ближайший к центру пиксель исходной ячейки по формуле
`(2*i+1)*source_size/(2*output_size)`. Так один алгоритм преобразует исходные
маски KanjiVG/Noto и растр кандидата. Далее применяется симметричное расстояние
Chamfer между центрированными масками: среднее расстояние от каждого набора
пикселей до ближайшего пикселя другого набора, нормированное на размер маски.
Для PNG на тёмном фоне пиксели кандидата сравниваются с KanjiVG и Noto Serif JP;
берётся меньшая из двух дистанций.
Ближайший другой символ Unicode ищется по объединению всех подходящих закреплённых
каталогов KanjiVG и Noto Serif JP, чтобы обе метрики ожидаемого и конкурирующего
символов учитывали тот же набор шрифтов. Версия валидатора —
`kanjivg-r20250816-5581e65d-noto-serif-jp-24fc2d26-ea6231b1-mask64-v6`. Пороговые значения входят
в контракт валидатора:

- `VERIFIED`: расстояние до ожидаемого эталона ≤ `0.020` и отрыв от ближайшего
  другого эталона Unicode ≥ `0.004`;
- `REJECTED`: расстояние до ожидаемого эталона хуже ближайшего эталона не менее чем на
  `0.015`;
- между этими условиями — `UNCERTAIN`;
- невалидные, повреждённые или пустые байты — `CORRUPT`; отсутствие эталона — `UNCERTAIN`.

Изменение порогов требует новой версии валидатора и соответствующего набора
регрессионных тестов. Неуверенное совпадение остаётся `UNCERTAIN`, а неподходящие пиксели не
подтверждаются по имени файла, статье или сведениям о происхождении.

Политику порогов можно воспроизводимо проверить без сети на закреплённых каталогах:

```bash
cargo test -p asset-store offline_threshold_calibration -- --nocapture
```

Контрольный прогон берёт 16 глифов из закреплённого каталога Noto Serif JP,
равномерно выбранных по порядку Unicode, строит для них синтетические плитки,
отрисованные в масштабе 142 px, и считает положительные расстояния до эталона,
отрыв и статусы. Для каждого образца он также проверяет ближайшую конкурирующую
идентичность Unicode и запрещает ей статус `VERIFIED`. Запуск печатает число
положительных результатов по статусам, максимальное расстояние до эталона,
минимальный отрыв, максимальную разницу для чужой идентичности и результаты её
проверки. Набор зафиксирован встроенной базой эталонов и не зависит от сети,
ручной приёмки изображений или текущего плана символов.

Для текущей версии валидатора v6 12 из 16 положительных синтетических случаев
получили `VERIFIED`, 4 — `UNCERTAIN`, 0 — `REJECTED`; максимальное расстояние до
эталона составило `0.002642`, минимальный отрыв — `0.001648`. Для ближайшей
конкурирующей идентичности все 16 случаев остались `UNCERTAIN` (0 `VERIFIED`,
0 `REJECTED`), а максимальная разница составила `0.012586`. Эти результаты не
меняют пороги.

Детерминированные контрольные и регрессионные тесты используют встроенные
каталоги Unicode и синтетические байты растра. Они проверяют:

- точную маску KanjiVG в PNG и анимированном GIF;
- тёмную PNG-плитку в стиле Yarxi с рамкой по Noto Serif JP и отказ для неверной
  идентичности Unicode;
- тёмную плитку, отрисованную в заданном масштабе, и отказ для близкой, но неверной идентичности Unicode;
- GIF формы Yarxi `полный кадр → постепенная прорисовка → полный кадр`; проверяется
  итоговая полная семантическая маска, а не номер выбранного кадра;
- близкие, но неверные идентичности;
- увеличение толщины и обрезанный кадр;
- повреждённые сигнатуры и потоки кадров, пустое изображение и отсутствующий эталон;
- границы порогов расстояния, отрыва и отклонения.

Калибровочный набор покрывает закреплённые эталонные глифы и ближайшие похожие,
но неверные идентичности. Он не оценивает долю ложных подтверждений для реальных
изображений Yarxi или для всего множества действующих источников. Результат
контрольного прогона не заменяет ручной просмотр PNG из рабочего источника; при
недостаточном отличии валидатор оставляет решение
`UNCERTAIN`.

## Команды

Запускайте из корня рабочего пространства:

```bash
# Идемпотентно получить и проверить один или несколько кандзи.
cargo run --locked --bin kanji-assets -- \
  --output json ensure 漢 字

# Проверить только новые или устаревшие решения проверки.
cargo run --locked --bin kanji-assets -- --output json validate --mode new

# Перепроверить все ресурсы.
cargo run --locked --bin kanji-assets -- --output json validate --mode full

# Просмотреть состояние и детерминированный план проверки.
cargo run --locked --bin kanji-assets -- --output json list
cargo run --locked --bin kanji-assets -- --output json plan \
  --mode new --validator-id kanjivg-pixel-chamfer \
  --validator-version kanjivg-r20250816-5581e65d-noto-serif-jp-24fc2d26-ea6231b1-mask64-v6

# Вручную импортировать локальный кандидат (он останется в состоянии pending).
cargo run --locked --bin kanji-assets -- --output json ingest \
  --character 漢 --file ./candidate.png

# Создать пакет (ID генерируется автоматически) и пройти до пяти раундов обхода по ширине.
cargo run --locked --bin kanji-assets -- --output json batch start 漢 字
cargo run --locked --bin kanji-assets -- --output json batch run --batch-id <id>

# Продолжить пакет позже, посмотреть состояние в JSON или записать локальный HTML-отчёт.
cargo run --locked --bin kanji-assets -- --output json batch status --batch-id <id>
cargo run --locked --bin kanji-assets -- --output json batch review --batch-id <id>

# Применить явное решение пользователя по точному SHA-256.
cargo run --locked --bin kanji-assets -- --output json batch decide \
  --batch-id <id> --character 漢 --sha256 <sha256> \
  --action confirm --reason "пользователь подтвердил текущий кандидат"

# После серии технических сбоев разрешить новое поколение получения.
cargo run --locked --bin kanji-assets -- --output json batch retry \
  --batch-id <id> --character 字 --reason "источник снова доступен"
```

`--store <path>` задаёт корень хранилища, а `--repository-root <path>` — рабочую
копию для проверки границы `decks/`. Обработка строго проверенной страницы
TLS-предупреждения Yarxi включена по умолчанию; `--allow-insecure-tls=false`
требует валидный сертификат. `ensure` сохраняет только фактически
подтверждённые записи `VERIFIED`; повтор уже доверенного SHA не обращается к
сети.

`list`, `plan` и `validate` открывают хранилище; открытие может создать файлы
состояния, восстановить незавершённую операцию или перенести прежние записи через
границу `.runtime`. Сама выборка `plan` не записывает данные. `changed: false` не означает,
что открытие было только для чтения. `validate`
запускает основной валидатор: `new` выбирает отсутствующие или устаревшие решения,
`full` перепроверяет весь манифест. Любой неуспешный статус проверки попадает в
карантин; код завершения ненулевой, если запрошенная цель не `VERIFIED`.

JSON-ответ содержит `schema_version`, `operation`, `store`, `mode`, `assets`,
`changed`, `conflicts`, `blockers` и `outcome`; ошибка добавляет стабильные
`error.code`, `category`, `message` и `details`. В `ensure` у каждой записи о ресурсе есть
поле `item_outcome`, поэтому успешные независимые результаты не скрывают
ошибки соседних символов.

`ingest` читает ровно один явно указанный исходный файл вне `decks/` и создаёт
кандидат со статусом `pending`. Формат и хеш определяются по байтам. Для замены
с проверкой ожидаемого состояния добавьте `--replace-expected-sha256 <текущий-hash>`.

### Пакетная обработка кандзи

`batch start [--batch-id ID] CHARACTER...` удаляет повторы идентичностей, создаёт
версионированное состояние в `.runtime/batches/<id>/` и до получения ресурсов
отмечает записи, которые владелец уже подтверждает как действующие `verified`.
Если передать существующий ID, должны совпасть запрошенный набор идентичностей и
валидатор; команда продолжит сохранённое состояние, а не начнёт новый пакет.

`batch run --batch-id ID [--rounds 1..5] [--interactive-review]` запускает до пяти
раундов получения ресурсов. Новые пакеты используют `kanji-single-candidate-v1`: технически
пригодный неопределённый или отклонённый кандидат сразу переходит в `awaiting_human`,
без повторного скачивания ради другой картинки и без повышения доверия усреднением.
Повторяемые технические ошибки по-прежнему ограничены пятью раундами. Каждый раунд обрабатывает всю текущую очередь до
следующего `retry`; опубликованные и уже действующие подтверждённые записи повторно
не запрашиваются. Ошибка отдельного элемента остаётся в `issues` и не отменяет
результаты соседних. Получение в браузере проходит без блокировки пакета. После
каждого фактического результата CLI повторно захватывает блокировку среды
выполнения, сверяет текущее поколение и число попыток, сохраняет байты
кандидата и `evidence`, а затем атомарно записывает состояние до запуска следующей
записи. Устаревший результат отбрасывается, если состояние элемента
изменилось во время получения.

`batch run` принимает `--workers` от `1` до `4`; значение по умолчанию — `4`.
Каждый обработчик использует собственную сессию браузера. Значение по умолчанию
выбрано сравнительным сетевым замером производительности на одинаковом наборе
из 300 кандзи.

Во время `batch run` прогресс сразу выводится в `stderr`: человекочитаемыми
строками в обычном режиме и JSON Lines при `--output json`. В JSON Lines каждое
событие имеет `schema_version: 1`, `operation: "batch_run"`, `event`, `batch_id`,
`elapsed_ms`, `round`, `round_limit`, `round_completed`, `round_total`,
`run_completed`, `batch_total`, `workers` и `in_flight`. Поля `identity`, `session`,
`worker_id`, `browser_session_id`, `attempt`, `generation`, `owner_attempt`,
`item_elapsed_ms`, `outcome` и `reason` появляются только при наличии контекста;
они не обязательны для каждого события. Человекочитаемый вывод также показывает
доступный контекст обработчика, сессии и попытки владельца.
В пуле `heartbeat` отправляет только координатор для активных назначений,
включая подготовку сессии; heartbeat внутреннего получения не дублируется.

`stage_timings` — необязательный массив объектов `{ "stage": "…", "duration_ms": N }`.
Он добавляется к `item_checkpointed` и `item_discarded_stale`, если поставщик передал
диагностику получения; массив может быть пустым. Эти значения отражают измеренные
этапы получения до проверки результата и записи контрольной точки. Подробный
диагностический журнал дополняет их проверкой и сохранением результата, поэтому
публичный массив не заменяет журнал всех этапов.

Стабильные значения `event`: `run_started`, `round_started`,
`browser_session_started`, `browser_session_ended`, `browser_session_rotated`,
`browser_session_bootstrap_started`, `browser_session_recovery_started`,
`worker_assigned`, `worker_retired`, `worker_stopped`, `worker_exhausted`,
`item_started`, `retry_started`, `retry_recovery_started`, `heartbeat`,
`item_checkpointed`, `item_discarded_stale`, `item_deferred`, `item_requeued`,
`round_finished`, `run_stopped`, `run_finished`. Ошибка отдельного получения
сохраняется как исход элемента; отказ CDP/монитора, тайм-аут или отказ восстановления
страницы отражается в причине завершения сессии. Здоровье монитора проверяется
после подтверждённого checkpoint, включая последний элемент; уже сохранённый
исход не отменяется и не назначается повторно. Если после обнаруженного отказа
монитора очередь закончилась и здоровье сессии не подтверждено новым получением,
запуск возвращает ошибку с сохранёнными исходами. При наличии хвоста
восстанавливается только сессия для ещё не завершённых элементов. Отказ записи/целостности и ошибка
очистки останавливают выполнение, а не запускают автоматическое восстановление.
При начальной подготовке сессии повторяется только отказ готовности среды
`browser_session_setup_runtime_unhealthy`. Ошибки запуска браузера, TLS и другие
ошибки подготовки сразу останавливают запуск с исходной причиной; они не
превращаются в исчерпание бюджета восстановления обработчиков.
`round_completed` увеличивается только после надёжного сохранения контрольной
точки. При `--output json` `stdout` по-прежнему содержит один самостоятельный
итоговый JSON-ответ команды; данные о ходе выполнения с ним не смешиваются.

Каждый запуск получения через `kanji-assets batch run` или исполнитель пакета тонового акцента
(`pitch-assets ensure`, `batch run` и `batch resume`) создаёт отдельный подробный
журнал в служебном каталоге пакета:
`<store_root>/.runtime/batches/<batch_id>/logs/<run_id>.jsonl`. Каталог и файл
создаёт `SafeBatchRuntime` относительно проверенной границы, без перехода по
символическим ссылкам и без перезаписи журнала другого запуска. Путь возвращается
как необязательное поле `diagnostic_log` в итоговом JSON, в том числе при ошибке;
в человекочитаемом режиме он печатается в `stderr` при старте.

Журнал содержит JSON Lines с временными метками, уровнем, модулем и
структурированными полями выполнения. В нём остаются безопасные сообщения
типизированных ошибок и сведения о сессиях, этапах JPDB, контрольных точках,
`CAS` и остановке; DOM, cookie и заголовки авторизации не записываются. При
`--output json` подробная диагностика идёт только в файл, а `stderr` сохраняет
поток JSONL с событиями прогресса без форматированных строк диагностики. Обычный
режим может дополнительно показывать читаемые tracing-сообщения только в `stderr`;
`stdout` остаётся выводом команды.
События `browser_acquisition_*` имеют уровень DEBUG и остаются в файле: слой
человекочитаемого вывода принимает только INFO, а при `--output json` этот слой
отключён и `stderr` сохраняет отдельный поток JSONL-прогресса.
Журнал создаётся до начала получения, а команда ждёт записи всех событий перед
возвратом.

В этом журнале общая схема фиксирует длительность элемента браузерного получения
и его этапов отдельными DEBUG-событиями `browser_acquisition_item` и
`browser_acquisition_stage` с `schema: "browser_acquisition_v1"` и
`schema_version: 1`. У события элемента `stage` равен `item`; `stage_duration_ms`
измеряет время текущего этапа, а `item_duration_ms` — накопленное время элемента
с момента его запуска. В пакете тонового акцента каждая назначенная попытка получает
собственный таймер, который передаётся от исполнителя через провайдер и координатор до
сохранения исхода с CAS. У Yarxi таймер охватывает внутренние повторы и паузы между
ними, проверку кандидата и контрольную точку CAS. Итоговая длительность элемента
включает получение, итоговую проверку и сохранение результата. При запуске только
провайдера JPDB таймер завершается на границе получения, поскольку у него нет
контрольной точки владельца. Длительности измеряются монотонными часами.

Обязательные поля каждого события: `event`, `schema`, `schema_version`, `provider`,
очищенная `identity`, `attempt`, `generation`, `stage`, `stage_duration_ms`,
`item_duration_ms`, `outcome` и `retryable`. Поля `worker`, `worker_session`,
`browser_session`, `failure_code`, `stop_reason` и `runtime_snapshot` записываются,
когда для них есть значение. Для JPDB `provider` равен `jpdb`, а для Yarxi —
`yarxi-suu-browser`. В исполнителе пакета тонового акцента значения `worker` и `worker_session`
обозначают исполнителя и его локальную сессию браузера; в других контекстах они
могут отсутствовать. `browser_session` — диагностический идентификатор браузерной
сессии. `provider`, `outcome`, `failure_code` и `stop_reason` ограничены безопасными
токенами; недопустимые значения заменяются на `redacted`. `identity` ограничена
256 байтами и очищается перед записью. `failure_code` и последний `runtime_snapshot`
передаются при отказе или прерывании, если снимок доступен, а `stop_reason` отдельно
объясняет остановку. `retryable` отражает решение провайдера о возможности повтора,
а не сам факт повтора. `generation` равен
поколению владельца в пакете kanji и `null` при запуске только провайдера без такого
контекста; фиктивный ноль не используется. Если после предметного результата
возникает сбой монитора или сессии, элемент сохраняет свой исход, а `stop_reason` и
свежий снимок связывают его с остановкой очереди.

Значения `stage` принадлежат фактическим границам выполнения. JPDB использует
`browser_launch`, `configure_browser`, `request_validation`, `search_resolution`,
`search_navigation`, `search_readiness`, `detail_navigation`, `detail_readiness`,
`detail_verification`, `pitch_inspection`, `capture`,
`post_capture_verification`, `candidate_validation`, `outcome_validation` и
`checkpoint`. Последние три стадии относятся к проверке результата и сохранению
исхода пакета тонового акцента; `checkpoint` включает повторное получение блокировки,
перечитывание состояния, CAS и сохранение. На пути перенаправления сразу к
словарной странице `detail_navigation` может отсутствовать. Если альтернативный
`PitchRunDriver` использует реализацию по умолчанию, полное получение отмечается
стадией `provider_acquisition`; рабочий драйвер JPDB фиксирует конкретные стадии
провайдера. Yarxi использует `search_submission`, `information_tab`,
`article_verification`, `media_readiness`, `media_selection`, `dark_theme`,
`resource_read`, `font_sample_capture`, `retry_backoff`, `retry_recovery`,
`semantic_validation`, `final_validation` и `checkpoint`. Последние три стадии
охватывают семантическую проверку изображения, итоговую проверку кандидата и
контрольную точку CAS соответственно. Вложенные и параллельные длительности могут
перекрываться, поэтому их нельзя складывать как последовательные интервалы.
Успешный этап имеет `outcome: "success"`; у элемента JPDB
успешные исходы — `acquired`, `no_pitch_accent_on_source`,
`ambiguous_vocabulary` и `vocabulary_not_found`. Ошибки и
прерывания отмечаются как `failure` и `interrupted`; их коды причин передаются в
`failure_code`, а предметный исход элемента Yarxi при успехе — `success`.

`runtime_snapshot` — JSON-проекция последней телеметрии CDP, вложенная как строка
и ограниченная 32 КиБ. Она содержит `epoch`, счётчики `pending_request_count`,
`network_failure_count` и `http_error_count`, до 16 примеров каждого вида в
`pending_requests`, `network_failures` и `http_errors`, а также
`javascript_exceptions` и `monitor_failed`. Устаревшая эпоха имеет отдельные
`stale_pending_request_count`, `stale_network_failure_count`,
`stale_http_error_count` и коллекции `stale_pending_requests`,
`stale_network_failures`, `stale_http_errors`; исключения JavaScript разделены на
текущую, начальную и устаревшую группы. Каждая текущая и устаревшая коллекция ограничена
16 записями. Запись примера содержит
`request_key`, тип ресурса, эпоху, признак текущей эпохи и верхнеуровневого
запроса, возраст наблюдения, HTTP-статус и категорию сетевой ошибки; вместо сырых
ID запросов используются SHA-256-ключи. URL, заголовки, cookie, DOM и исходные
CDP-сообщения в снимок не попадают. Если он превышает лимит, остаётся компактный
объект с `truncated: true`, текущей `epoch`, текущими и устаревшими счётчиками,
разбивкой JavaScript-исключений и `monitor_failed`; счётчики берутся из той же
диагностической проекции, что и обычный снимок.

Эти события описывают получение одного элемента и его этапы, а события прогресса
`browser_session_started`, `browser_session_ended` и `browser_session_rotated`
остаются отдельными записями жизненного цикла сессии. Общий `browser_runtime`
пишет события `event: "browser_lifecycle"` о жизненном цикле: остановке транспорта,
принадлежащего процессу, обработчиков CDP, телеметрии и удаления профиля или
временного каталога. Исход транспорта не подменяет итоговые условия очистки:
отсоединённый транспорт считается безвредным только при доказанной остановке
процесса и успешном удалении принадлежащих ему каталогов. Нарушение этих условий
остаётся `browser_cleanup_failed`; сбои внешнего рабочего каталога запуска
сохраняют код `temp_workspace_cleanup_failed`.

Пример выборки ошибок из одного запуска:

```bash
jq -c 'select(.level == "ERROR") | .fields' \
  <store_root>/.runtime/batches/<batch_id>/logs/<run_id>.jsonl
```

Срок в 20 минут относится к одной сессии браузера. Если он истекает до начала
обработки следующей записи, сессия закрывается, а оставшаяся очередь продолжается
в новой сессии. Таймаут или ошибка восстановления страницы могут дать технический
исход только фактически начатой записи; незапущенный хвост остаётся в состоянии
`pending` и не получает попыток, изменений `generation` или агрегированных
показателей. До `browser_session_started` Yarxi проверяет чистое состояние среды
выполнения новой сессии: отсутствие ожидающих запросов, сетевых и HTTP-ошибок,
JS-исключений и отказа монитора. Если остались только ожидающие запросы, Yarxi
ждёт их завершения не более 20 секунд; сетевые или HTTP-ошибки, JS-исключения и
отказ монитора сразу делают среду выполнения неготовой. При истечении ожидания или таком
сбое среды выполнения текущая сессия закрывается, а та же точка очереди повторно
подготавливается максимум в двух новых сессиях подряд без создания попыток для
элементов. После успешной подготовки счётчик сбрасывается. Ошибки очистки и
другие ошибки подготовки
останавливают команду и сохраняют уже обработанную часть пакета; следующий
запуск `batch run` продолжает с оставшихся записей. На `Ctrl+C` провайдер
закрывает текущий сеанс браузера и завершает команду после текущего сохранённого
результата; запись без итогового сохранения остаётся доступной для повторного
получения в том же `batch_id`.

До автоматической публикации попытка и байты кандидата записываются в служебное
хранилище пакета (`.runtime`).
Единственный кандидат со статусом `VERIFIED` проходит проверку владельца домена
и атомарно публикуется по каноническому пути. В сохранённых пакетах прежней политики для различных технически валидных
хешей рассчитывается сводка среднего, минимума, максимума и количества значений
`expected_distance` и `nearest_margin`; одинаковый SHA не увеличивает
число образцов. `kanji-distinct-mean-v2` сохраняет исходные пороги `0.020` и
`0.004`, требует прохождения порога отрыва от ближайшего эталона для выбранного
кандидата и фиксирует его точный SHA. Сводное доверие не заменяет автоматический
статус самого выбранного кандидата: версия и свидетельства сводки сохраняются
отдельным решением.

После исчерпания технических повторов элементы без кандидата получают состояние
`awaiting_human`. Пригодные неопределённые кандидаты новых пакетов ждут человека
уже после первой сохранённой попытки.
`batch review` создаёт локальный игнорируемый HTML-отчёт с анимированными GIF,
всеми различными изображениями кандидатов, точными SHA, результатами автоматики,
свидетельствами каждой попытки и сводными метриками. Кандидаты остаются в
`candidates/` по путям, полученным из их хеша; HTML не является источником истины.

`batch decide` принимает только структурированные `confirm`, `reject` или
`reacquire` для текущих `--character` и `--sha256`. `confirm` требует технически
корректных байтов GIF/PNG, точного сравнения и замены ожидаемого SHA источника,
автоматических свидетельств от владельца домена и полной расшифровки изображения
до одобрения человеком. `reject` сохраняет решение человека для точного
кандидата и отправляет только эту идентичность в новое поколение получения.
`reacquire` планирует целевой повтор без решения о семантической пригодности.
Для элемента после пяти технических ошибок без кандидата используй `batch retry`
без `--sha256`; при наличии кандидата CLI требует `--sha256`.

`batch status` возвращает состояние, а `batch review` также создаёт отчёт.
JSON набора содержит `batch_id`, `counts`, список `items`, ошибки элементов
`issues`, `blockers`, необязательный `review_artifact` и полное состояние и
свидетельства `batch`. `run` возвращает код `0` только при полном разрешении
ресурсов в каноническом хранилище и код `3` при ожидании решения человека или
частичном продвижении; отдельные ошибки остаются привязаны к идентичности.
`start`, `status`, `review`, `decide` и `retry` возвращают `0` при успехе;
системные ошибки границы, схемы и целостности используют стандартные коды
возврата владельца ресурсов.

После перезапуска процесса продолжай с тем же ID: `status` → `run`/`review` /
`decide`. CLI возобновляет точную публикацию владельца из сохранённых кандидата
и намерения решения человека без повторного получения. Служебное состояние `.runtime`,
HTML и байты кандидатов не входят в канонический корпус и не предназначены для Git.

### Текстовый пакет решений и явная интерактивность

Обычный запуск, пайплайны и JSON не задают вопросов и не открывают приложения.
Для ручного запуска с полным TTY явно укажите opt-in:

```bash
cargo run --quiet --locked --bin kanji-assets -- batch run --batch-id ID --interactive-review
# Вернуться к сохранённым кандидатам без получения из сети:
cargo run --quiet --locked --bin kanji-assets -- batch review-interactive --batch-id ID
```

При наличии кандидатов после завершения получения и закрытия браузерных ресурсов
появляется вопрос `[y/N]`. Ответ `y` или `Y` создаёт производный пакет и
запускает файловый менеджер и редактор. После сохранения файла нужно отдельно
ответить `y` или `Y` на предложение применить: завершение GUI-процесса само по
себе ничего не применяет.
Отказ, EOF, Ctrl+C и ошибка запуска сохраняют кандидатов и завершённую работу.
Пустая очередь не вызывает приглашения. Блокировка пакета не удерживается во время
редактирования. При ошибке получения интерактивная фаза не начинается.

Без GUI доступны команды:

```bash
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-export --batch-id ID
# Отредактировать указанный review_artifact, затем применить его review_id:
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-apply --batch-id ID --review-id FULL_REVIEW_SHA256
```

`review-export` возвращает `review_id` и путь `review_artifact` к `decisions.tsv`.
Каталог `.runtime/batches/<id>/review-<review_id>/` содержит снимок метаданных,
редактируемый UTF-8 TSV, `index.html` для просмотра групп предложений
и отдельные проверенные копии GIF/PNG с именами
`<Unicode>-<полный SHA>.<ext>`. Для обычных пакетов изображения также
встраиваются в HTML, поэтому просмотр через Windows/WSL не зависит от длинных
путей к отдельным файлам. Общий бюджет встраивания — 32 МиБ исходных
изображений; сверх него остаются относительные ссылки на копии.
Оригиналы не меняются. Повторный export того же
снимка сохраняет заполненный файл. Изменённые копии изображений отклоняются
при повторном открытии и применении. Для получения только HTML по-прежнему есть
`batch review`.

В `decisions.tsv` меняется только первая колонка, разделитель — TAB:

- `y` подтверждает **точные байты** текущего кандидата;
- `e` отклоняет непригодное изображение;
- один другой допустимый Han отклоняет с причиной `actual_character=<Unicode>`;
- пустое поле и `-` оставляют запись без решения.

BOM/CRLF и строки комментариев `#` поддерживаются. Произвольное слово, изменение
остальных колонок, подписи, схемы, batch, поколения, числа попыток, SHA или пути,
пропущенные, дополнительные и повторные строки отклоняют файл **целиком**.
Принимается только `decisions.tsv` выбранного снимка; backup и скрытые файлы
не сканируются. Недоверенные пути и symlink не открываются. Снимок адресуется
SHA своих метаданных, а актуальность каждой строки сверяется с состоянием владельца.

Сначала все строки проверяются под блокировкой, затем `KanjiBatch::decide` для
всех решений атомарно сохраняется в обычное состояние пакета. Его
`human_decisions` — единственный журнал намерений: отдельного источника доверия нет.
Публикация выполняется через штатные decode/SHA/CAS и человеческое подтверждение
владельца. При сбое после сохранения намерений повтор `review-apply` или `batch run`
продолжает публикацию; уже применённые строки идемпотентны и не подтверждают
новое поколение, даже если оно получило тот же SHA. Ошибки публикации отражаются
в `issues` и коде `3`, а сводка `review_decisions` показывает применённые,
подтверждённые, отклонённые, пропущенные и уже применённые решения.

Отказы файла используют действие `reject_and_hold` и состояние `rejected`:
автоматического повторного получения нет. Для осознанного повтора этой записи
нужен `batch retry --batch-id ID --character 漢 --reason 'явный повтор'` без SHA,
поскольку текущий кандидат уже отклонён. Прежнее действие `batch decide reject`
сохраняет прежнее поведение с планированием нового поколения. Неверный символ
никогда не становится новой идентичностью и не переименовывает изображение.

`--interactive-review` и `review-interactive` несовместимы с `--output json`:
отказ происходит до открытия store и получения. Также запрещены неполный TTY,
`TERM=dumb`, окружение CI/`CODEX_NONINTERACTIVE` и потомки `cargo test` или
test harness, включая запуск через PTY. Запуск через `cargo run` разрешён.
Процесс должен принадлежать foreground group терминала: фоновые job не задают
вопросы. Обычный `cargo test` не запускает эту границу приложений.

Для `decisions.tsv` сначала пробуется настроенный текстовый редактор;
при его отказе файл открывается десктопным
приложением, назначенным именно на `text/plain`, чтобы табличный редактор,
связанный с `.tsv`, не переписал формат решений (`xdg-mime` и `gtk-launch`; при отсутствии `gtk-launch` доступен
`gio launch` для найденного desktop-файла этой ассоциации).
Каталог сначала открывается Linux-ассоциацией по MIME (`xdg-open`).
При её отказе или без Linux desktop в сессии WSL с включённым binfmt-флагом
interop используется Windows Explorer: сначала через `PATH`, затем по
проверенному пути Windows, преобразованному посредством `wslpath`.
Для Windows-приложений UNC-адрес `\\\\wsl.localhost\\...` сокращается до
поддерживаемого Windows `\\\\wsl$\\...`, что уменьшает вероятность ограничения
длины пути. Если даже сокращённый путь остаётся слишком длинным для конкретного
редактора, используйте Linux-редактор или откройте пакет из более короткого
расположения.
Если пользователь не выбрал редактор, а Linux-ассоциация `text/plain`
недоступна, WSL interop позволяет дополнительно попробовать Windows Notepad;
этот путь необязателен и требует исполняемую программу. Для слишком длинных
даже после сокращения путей Notepad выводится отказ с советом использовать
Linux-редактор или короткое размещение хранилища.
Для явно настроенного Windows-редактора Explorer не требуется; interop должен
быть включён. Windows-путь программы переводится через `wslpath -u`, а путь TSV
для редактора `.exe` (включая имя в `PATH` и путь `/mnt/...`) — через `wslpath -w`.
Ошибки преобразования, запуска и завершения диагностируются.
Обязательной зависимости от Windows, WSL или `notepad.exe` нет:
если открывать нечем, команда печатает абсолютные пути каталога и
файла решений и подсказку про `review-export` и `review-apply`. Редактор выбирается
в порядке `GIT_EDITOR`, `core.editor`, `VISUAL`, `EDITOR`; разрешены кавычки и
аргументы с пробелами, но shell-команды, подстановки и pipeline не поддерживаются.
Отказ конкретного запуска диагностируется отдельно для каталога и TSV;
успешное открытие каталога не означает успешного открытия редактора. Если все
попытки запуска завершились ошибкой, команда сообщает ошибку и оставляет пакет
для `review-export`/`review-apply`. Настроенный редактор — доверенная программа
пользователя: запрет shell-синтаксиса не является песочницей. Настройка редактора
должна быть UTF-8; non-UTF8 путь самого TSV передаётся Linux-программе без потерь.
Редактор запускается напрямую; текст решений не является командой. Завершение
запущенного процесса ничего не подтверждает и не применяет: применение выполняет
явное подтверждение человека, после которого файл решений читается заново.
На сервере без `DISPLAY`/`WAYLAND_DISPLAY` настроенный терминальный редактор
доступен только в этом явном интерактивном режиме; при отсутствии приложений
печатаются пути и команды для ручной работы. Desktop-пакеты не устанавливаются.

Старые пакеты с `kanji-distinct-mean-v2` продолжают читаться с прежними правилами.
Явная команда `batch revalidate --batch-id ID` повторно проверяет сохранённые
байты текущим валидатором и декодером и атомарно переводит пакет на
`kanji-single-candidate-v1` без сетевого получения или фиктивных попыток.
Старые подтверждения человека остаются в `human_decisions` и сохраняют привязку
к точному SHA. Если те же байты проходят текущую техническую проверку и не имеют
статуса `Corrupt`, подтверждение продолжает определять `HumanVerified`; иначе оно
остаётся исторической записью, эффективный статус выводится заново, а признаки
публикации очищаются. `ExistingVerified` остаётся под доверием владельца и после
миграции сверяется с актуальным снимком канонического store. Старый автоматический
статус не переносится между различными версиями валидатора; старый редакторский
снимок после изменения состояния или версии нужно экспортировать заново.

### Необязательные слепые OCR-предложения Ollama

`batch ocr` обрабатывает **уже сохранённый** пакет, последовательно. Обычные
`start/run/status/review`, чтение подтверждённых ресурсов и pitch-accent не
обращаются к Ollama. Сначала владелец проверяет целостность и актуальное доверие
канонического store: подтверждённые ресурсы переиспользуются. OCR доступен только
для текущих технически пригодных `awaiting_human` со статусом v6 `Uncertain`.
`Verified`, `Rejected`, `Corrupt` и разрешённые элементы не вызывают даже discovery
Ollama. Повторного скачивания с Yarxi нет.

```bash
# Обычный путь, без OCR:
cargo run --quiet --locked --bin kanji-assets -- batch start --batch-id my-kanji 漢 字
cargo run --quiet --locked --bin kanji-assets -- batch run --batch-id my-kanji

# Явно включить OCR сохранённых неопределённых кандидатов:
cargo run --quiet --locked --bin kanji-assets -- --output json batch ocr \
  --batch-id my-kanji --model 'qwen3.5:9b-q4_K_M' \
  --endpoint 'http://127.0.0.1:11434' --timeout-seconds 120

# Для Windows-host из WSL задайте реально доступный адрес вместо примера:
cargo run --quiet --locked --bin kanji-assets -- --output json batch ocr \
  --batch-id my-kanji --model 'qwen3.5:9b-q4_K_M' \
  --endpoint 'http://192.168.1.2:11434' --allow-remote

# Получить TSV и index.html рядом с ним; решения изначально пустые, '-' означает явный пропуск:
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-export --batch-id my-kanji
# После просмотра группы совпадений оставьте подтверждаемые строки пустыми, '-' поставьте для пропуска;
# внесите явные решения для остальных строк в TSV.
# Команда применит их вместе с подтверждённой группой совпадений.
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-confirm-matches \
  --batch-id my-kanji --review-id FULL_REVIEW_SHA256 --confirm-reviewed
# После применения группы создайте новый снимок для оставшихся строк.
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-export --batch-id my-kanji
# Внесите оставшиеся решения и примените с новым review_id:
cargo run --quiet --locked --bin kanji-assets -- --output json batch review-apply \
  --batch-id my-kanji --review-id NEW_REVIEW_SHA256
# Явный повтор OCR, включая сохранённые отказы:
cargo run --quiet --locked --bin kanji-assets -- --output json batch ocr \
  --batch-id my-kanji --model 'qwen3.5:9b-q4_K_M' --rescan
```

После применения группы создайте новый `review-export` для оставшихся строк:
их состояние изменилось, прежний снимок содержит уже применённые строки.
`review-confirm-matches` использует ту же полную проверку TSV, SHA, generation,
копий и атомарный журнал `human_decisions`, что `review-apply`. Он добавляет
подтверждения только для пустых строк совпавшей группы; `-` явно пропускает строку.
Явно заполненные решения TSV тоже применяются. `--confirm-reviewed` означает, что человек просмотрел
изображения, включая возможность ошибочного совпадения OCR. Создание или открытие
отчёта не подтверждает ничего. Порядок строк — совпадения, несовпадения,
нераспознанные/отказы, без OCR. Дополнительные TSV-колонки — `observed`, совпадение,
отказ и ключ предложения — входят в защищённые метаданные и не редактируются.
Старые снимки без этих колонок продолжают читаться.

Базовый URL поддерживает HTTP без credentials, пути, query и fragment.
Всё вне буквального loopback IPv4/IPv6 требует `--allow-remote`, включая DNS-имена
и приватный WSL-host: это явное разрешение отправить изображения выбранному
серверу. Proxy и HTTP redirects отключены. Ollama и модель устанавливает пользователь;
программа не загружает модели и не запускает сервер. `/api/tags` закрепляет digest
установленной модели, `/api/show` требует capability `vision` и отклоняет объявленный
`remote_host` облачной модели. Модель и адрес настраиваются; `127.0.0.1` из WSL
не считается автоматически доступным адресом Windows.

Инструкция `structure-v1` перенесена дословно из исследования Structure; её SHA-256
закреплён тестом. В `/api/chat` идут только универсальная инструкция и base64 PNG:
ожидаемый Unicode, путь, имя исходного файла и контекст статьи не передаются.
Используются `stream=false`, `think=false`, `temperature=0`, `num_predict=128`,
`num_ctx=4096` и JSON schema с единственным строковым `observed`. Принимается
ровно один поддерживаемый Han/CJK либо `?`, без нормализации вариантов Unicode.
Ответ с лишними полями, объяснением, многосимвольным `observed`, неполный ответ
и `done_reason=length` сохраняются как отказ предложения.

Подготовка берёт исходные сохранённые байты и SHA. Ограниченный декодер v6
определяет полный репрезентативный GIF-кадр; повторный bounded decode получает
именно этот композитный кадр. PNG декодируется целиком. Прозрачность компонуется
на белый фон, затем `image` выполняет Lanczos3 2× и кодирует один PNG.
Это самостоятельная реализация Lanczos3 в Rust: пиксельное совпадение с прежним
PowerShell/System.Drawing не обещается. Исходник ограничен 8 МиБ, сторона 2048,
GIF 512 кадрами, декодер 32 МиБ; выход 4096×4096 и 8 МиБ. Сетевой ответ ограничен
1 МиБ, запрос и чтение ответа — `--timeout-seconds` (1–600, по умолчанию 120).
Одна модельная операция выполняется за раз; отмена процесса оставляет атомарные
checkpoint предыдущих элементов, прерванный запрос можно повторить.

Предложения находятся только в `.runtime/batches/<id>/ocr/suggestions.json`:
identity, исходный и подготовленный SHA, формат/кадр/размер, provider, URL, model,
digest, версия и SHA инструкции, версия преобразования, параметры генерации,
timeout, timestamp и тип
отказа. Кэш связан с точными байтами и настройками. Повторный явный OCR проверяет
метаданные модели через discovery, затем на cache hit делает **0 `/api/chat`**.
Перед и после распознавания digest перечитывается: смена модели во время
запроса сохраняется как отказ `model_changed_during_scan`, без `observed`.
Изменение SHA/model/digest/prompt/transform не выдаёт прежнюю запись за новый
результат. Сохранённое предложение и HTML доступны без повторной сети.
Отказ discovery сохраняется с digest `unavailable`; успешное discovery позже
создаёт другой ключ. Повтор отказа `/api/chat` с прежними настройками требует
`--rescan`. Во время сети runtime lock снимается; после возвращения проверяются
текущие SHA, generation и кандидат. Устаревший результат не записывается.

JSON команды содержит `ocr_summary` (`saved`, `cache_hits`, `chat_requests`).
Сохранённый отказ провайдера возвращает код `3` и `issues` для точной identity;
кандидат и его автоматическое решение не меняются. При ошибке дисковой границы
используется обычный код `AssetError`. OCR не присваивает `AutoVerified` или
`HumanVerified`, не переименовывает чужой Unicode и не является валидатором доверия.
Обновление необязательной модели не переоценивает подтверждённые канонические ресурсы.

## Проверки

Локальные тесты получения ресурсов и проверки изображений не обращаются к сети;
они используют только синтетические данные и временные каталоги. Получение данных
в браузере выполняется отдельно против сайта и не входит в основной набор тестов.
Проверки рабочего пространства запускаются из корня:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Корневое рабочее пространство Cargo остаётся единственной точкой сборки.
`decks/**/media/` не используются как тестовые данные или источники.
