# Контроль дискового мусора

**Русский** · [English](README.en.md) · [简体中文](README.zh-CN.md)

`repository-maintenance` — отдельный пакет Cargo для наблюдения за локальными
артефактами и безопасной очистки воспроизводимых данных. Он отделён от
`anki-repo`, потому что не работает с CrowdAnki-экспортами и отвечает за
жизненный цикл диска.

## Что нашёл аудит

На текущем `HEAD` источники распределены так:

| Область | Фактический источник | Политика |
|---|---|---|
| Рабочая область Cargo | Единственная корневая рабочая область; обычный каталог `target` определяется через `cargo metadata`. Профили сборки и тестов объявлены в корневом `Cargo.toml`. | Внутри рабочей области измеряются `target` и настроенный Cargo `build-dir`; очистка выполняется только через `cargo clean`. |
| Вложенные сборки | Проверка `code-review` в `anki-repo` запускает Cargo Clippy; синтетические сценарии Cargo задают `CARGO_TARGET_DIR` внутри своего `TempWorkspace`. | Временный каталог удаляет его владелец или существующий сборщик бесхозных каталогов. |
| Временные данные процессов, браузеров и тестов | `asset-store` создаёт `TempWorkspace` с приватным маркером владения; браузер получает отдельные профиль и `TMPDIR` внутри этого дерева. | Используются идентичность процесса, время запуска PID, ссылки на процессы, `NOFOLLOW` и границы точек монтирования из `asset-store`. Этот инструмент вызывает те же публичные пути сборщика мусора. |
| ZIP со свидетельствами | `tools/asset-store/src/bin/common/evidence_zip.rs` сохраняет архив в `<temp_dir>/anki-decks-evidence` либо по пути `--output`. | ZIP хранит свидетельства, поэтому новый сборщик мусора только показывает его в инвентаризации. По умолчанию каталоги и файлы без проверяемого маркера владельца не удаляются. Распознанные старые каталоги без маркера можно удалить только явной командой `clean --cleanup-legacy --apply`. Явный `--output` вне сканируемых корней не попадает в инвентаризацию. |
| Постоянное хранилище и транзакционные `.tmp`-файлы | Данные `asset-store` находятся в управляемом им каталоге; временные имена используются для атомарных операций и восстановления незавершённых переходов. | Это состояние предметной области, а не общий мусор Cargo; очистка диска его не затрагивает. |
| Постоянные внешние каталоги сборки Cargo | В исходном коде сейчас нет отдельного постоянно работающего процесса, создающего каталоги сборки Cargo под `~/.cache`. Случайные каталоги из локального инцидента не доказывают владение ими. | Для явных повторно используемых кэшей предусмотрены `cache init` и `cache run`: они создают маркер, обновляют время последнего использования и учитываются общим лимитом. Неизвестные каталоги не очищаются. |

Профили Cargo этим инструментом не меняются. Одноразовые сборки остаются
ограничены `TempWorkspace`; отдельные постоянные внешние тестовые каталоги
сборки не создаются.

## Границы владения

- Основной `target` определяется фактическим выводом `cargo metadata` и
  очищается, только если `target` и все учитываемые каталоги сборки находятся
  внутри текущей рабочей области, дерево не содержит ошибок или границ точек
  монтирования, есть
  штатный `CACHEDIR.TAG`, а проверка процессов не обнаружила занятый путь.
  Каталог `target`, направленный во внешний общий каталог, виден, но автоматически не
  очищается; если он превышает жёсткий предел, отчёт отмечает непроверенное владение
  как ошибку и возвращает ненулевой статус.
- Перед удалением проверяются границы каталогов сборки: корень рабочей области,
  деревья исходников и пересекающиеся каталоги не передаются `cargo clean` даже
  при наличии корректного `CACHEDIR.TAG`. Отсутствие обычного `target` не
  препятствует безопасной очистке отдельного подтверждённого `build-dir`;
  если каталог появился после планирования, требуется новая проверка.
- Настроенный отдельный `build-dir` очищается вместе с `target` одним вызовом
  `cargo clean`, поэтому оба каталога заранее подтверждаются штатным `CACHEDIR.TAG`.
  Если основной `target` отсутствует, существующий проверенный `build-dir`
  передаётся как оба пути: новый непроверенный `target` не затрагивается.
  Каталог без маркера не очищается. Маркер проверяется при выборе очистки
  (`ThresholdDecision::Clean`); отсутствие маркера тогда даёт `error` и сохраняет
  данные, а при `keep` или `warn` очистка не планируется и маркер не требуется.
- Внешний повторно используемый кэш создаётся только командой `cache init`.
  Маркер подтверждает канонический корень рабочей области, идентификатор кэша и
  относительный путь `target`. Каталог должен принадлежать текущему UID и быть
  закрыт от группы и остальных пользователей. `cache run` направляет каталоги
  `target` и `build-dir` Cargo в этот кэш и обновляет время последнего
  использования до и после команды. Сборщик мусора рассматривает только такие
  кэши.
- `--temp-root` и `std::env::temp_dir()` обходятся полностью; совпадающие
  канонические корни сканируются один раз.
  В отчёт входят общий размер выделенных блоков, число записей верхнего уровня и
  до N крупнейших записей. Разреженные файлы учитываются по выделенным блокам,
  жёсткие ссылки — один раз в каждом просматриваемом корне; символические ссылки
  не обходятся, границы других точек монтирования не пересекаются.
- `TempWorkspace` очищается существующим сборщиком, который проверяет владельца.
  Доказанно живой владелец, неизвестная ссылка PID на процесс, повреждённый маркер или ошибка проверки
  означают `deferred`/`error`, а не попытку удаления.
- Объекты других UID получают значение `foreign`, объекты без доказанного маркера —
  `unknown`. Каталоги, файлы и ссылки показываются и никогда не удаляются
  проектом; цели ссылок не обходятся. Ошибки доступа и пропущенные точки
  монтирования делают
  соответствующую инвентаризацию неполной; итоговая сумма тогда является только
  видимой нижней оценкой. Ошибка перечисления внешнего кэша прекращает запуск,
  чтобы сборщик мусора не использовал неполный список.
- UID владельца используется для этой классификации, но числовое значение не
  входит в отчёты. Компоненты временных путей вида `anki-decks-<UID>` выводятся как
  `anki-decks-<uid>`.
- `systemd-tmpfiles-clean.timer` показывается диагностически. Глобальную очистку
  чужих временных данных оставляют системе.

## Политика

Единственный отслеживаемый источник параметров по умолчанию — [`policy.toml`](policy.toml):

| Объект | Значение | Действие |
|---|---:|---|
| Порог предупреждения для основного каталога Cargo `target` | 12 GiB | Только предупреждение. |
| Жёсткий предел основного каталога Cargo `target` | 20 GiB | Режим `dry-run` предлагает полный `cargo clean`; `clean --apply` выполняет его после повторной проверки. |
| Жёсткий предел для внешних кэшей с маркером владения | 10 GiB | Очищать старейшие подходящие кэши, пока размер не станет не выше 5 GiB или кандидаты не закончатся. |
| Минимальный возраст внешнего кэша | 7 дней | Более свежий кэш пропускается. |
| Бесхозный `TempWorkspace` | Политика существующего владельца | Схема 1 требует TTL не менее 24 часов; схема 2 использует доказательство идентичности процесса и текущие ссылки. |
| Число крупнейших записей каждого корня инвентаризации | 20 | `--detail` показывает все записи верхнего уровня. |

`--policy FILE` переопределяет значения TOML. Для тестовых сценариев доступны
переопределения порогов в байтах и секундах, например
`target_hard_limit_bytes=2`; это позволяет
проверять решения на маленьких файлах, не занимая гигабайты.

## Первоначальная настройка и самодиагностика

Основной пользовательский CLI при первом интерактивном выполнении подходящих команд
(например, `anki-repo inspect EXPORT`) рекомендует включить автоматическое обслуживание,
показывает измеренный размер *подтверждённо* управляемых артефактов и спрашивает
`[y/N]`. Отказ и согласие сохраняются, а фактическая активность пользовательского
таймера systemd проверяется отдельно. При неинтерактивном запуске вопросов нет.

```bash
anki-repo maintenance status
anki-repo --json maintenance status | jq '.result | {preference, automatic, measurement, diagnostics}'
anki-repo maintenance enable
anki-repo maintenance disable
```

`maintenance status` использует тот же диагностический объект для текста и JSON.
Действующие границы `target`, зарегистрированных внешних кэшей и
`TempWorkspace` задаёт политика GC. Полный размер `/tmp` никогда не
выдаётся за размер кэша Anki-decks. Поле `measurement.complete` относится
ко **всему** обзору, включая чужие системные каталоги в `/tmp`.
Сводка `measurement.system_tmp` отделяет количество ошибок и границы mount
в этой общесистемной инвентаризации. Например, недоступный
`systemd-private-…` и отдельный mount в `/tmp/.X11-unix` означают
`system_tmp_inventory_incomplete` (диагностика уровня `info`), но **не**
`gc_operation_error`: доступные чужие каталоги могут просматриваться, но
не удаляются; границы mount не пересекаются.
Учтённый размер подтверждённых проектных артефактов показывается отдельно;
неполнота чужого `/tmp` не доказывает неполноту проверки `target`.
`measurement.managed_complete` отдельно подтверждает полноту управляемых объектов:
нет фатальных ошибок, владение `target` подтверждено, внешние кэши не содержат
неизвестных записей, проектные временные объекты проверены. Отсрочка живого
владельца не делает измерение ошибочным. `measurement.fatal_errors` считает
только ошибки GC; общесистемный обзор описан в `measurement.system_tmp`.
Итоговый `scan` продолжает сообщать все обнаруженные ошибки и
`complete=false` — ошибки не скрываются.

При `clean --apply` неполный обзор чужого `/tmp` может сохранить outcome
`partial` в последнем snapshot, но не вызывает графическое уведомление
об ошибке очистки. Уведомление о сбое отправляется при `fatal_errors > 0`.
В `last_attempt` добавлены необязательные `mode`, `fatal_errors` и
`managed_inventory_complete`; `inventory_complete` продолжает обозначать полноту
всего обзора. `outcome=partial` означает неполный обзор, включая чужой `/tmp`,
и сам по себе не означает ошибку очистки. Старые snapshot читаются с неизвестными
значениями новых полей (`null`). Формат сохраняет `schema_version=1`; старые
бинарники со строгим запретом неизвестных полей не смогут прочитать расширенный
snapshot и покажут `last_attempt_unavailable`, поэтому при откате бинарника
последний результат можно получить очередным запуском уже старой версии GC.

В snapshot сбоя `message` содержит первые 2000 Unicode-символов ошибки;
исходная ошибка GC возвращается целиком. Это ограничивает размер краткой
записи, включая сообщения парсера с длинными строками конфигурации.

Неизвестное/неполное измерение отмечается явно. JSON сохраняет стандартный конверт `schema_version, command, result`;
внутри `result` присутствуют `schema_version`, `preference`,
`automatic`, `installed_workspace`, `measurement`, `last_attempt` и
`diagnostics` с устойчивыми `code` и `severity`.
Автозапуск и текущее выполнение показаны отдельно: `timer_enabled`,
`timer_active`, `service_active`. `automatic=enabled` означает, что подтверждённый
таймер разрешён к автозапуску, активен сейчас или его служба ещё выполняется.
Поэтому комбинация `timer_enabled=false, timer_active=true` не выглядит
отключённой. При `yes` для полноценного обслуживания нужны оба факта `true`;
при `no` любой действующий факт вызывает `preference_mismatch`.
`timer status` и `maintenance status` используют один источник фактов.
Неизвестные ответы `systemctl` дают `unknown`, недоступный user-systemd —
`unavailable`; эти состояния не разрешают сохранить успешный отказ `no`.

Принадлежность установки подтверждается приватной конфигурацией, точными
управляемыми шаблонами на диске и свойствами загруженных unit:
`LoadState`, `FragmentPath`, `ExecStart`, `DropInPaths`, `NeedDaemonReload`.
Подменённый или устаревший unit, неизвестные drop-in и небезопасные ссылки/права
запрещают изменение установки. Отсутствующий установленный бинарник можно
восстановить повторным `enable`, если остальные доказательства совпадают.
Одна отметка владельца без подтверждённого checkout не разрешает
`maintenance disable`; для диагностики файлы сохраняются.

Обе операции `enable`/`disable` удерживают общую блокировку от проверки до
сохранения предпочтения. `yes` намеренно сохраняется при ошибке установки,
ошибка возвращается отдельно, повторный `enable` восстанавливает установку.
Отключение проверяет остановку таймера **и** службы перед удалением файлов,
а `no` сохраняется только при подтверждённом отсутствии автозапуска и активности.
Диагностические команды включают экранированный `--workspace-root` текущего
checkout; `clean` в рекомендациях является предварительным просмотром без
`--apply`. Текст показывает «да/нет/неизвестно», возраст попытки и русские
значения режима/результата; JSON сохраняет машинные значения.

Внешний JSON маскирует UID только в сегментах `anki-decks-<uid>`, включая
пути checkout и последней попытки. Приватный snapshot хранит точные пути для
сопоставления с текущим checkout. Исполняемые рекомендации содержат точный путь,
чтобы их можно было выполнить. Для путей с байтами вне UTF-8 диагностика
использует строковое представление с заменой невалидных байтов, а рекомендация
с путём не выдаётся (`action: null`). Приватный snapshot такие пути не заменяет:
ошибка сериализации возвращается вызывающему коду, прежний файл сохраняется.

Выбор пользователя хранится атомарно в
`${XDG_CONFIG_HOME:-~/.config}/anki-decks/gc-preference.json`.
В нём отдельно хранятся метки последней фоновой проверки объёма и последнего
показанного предупреждения: суточный интервал проверки расходуется на саму
проверку, поэтому отказ не заставляет повторять полный обход при каждом вызове,
даже пока пороги не превышены.
Компактное состояние последнего запуска `clean --apply` записывается
в `${XDG_STATE_HOME:-~/.local/state}/anki-decks/gc-last-attempt.json`.
Файл результата привязан к workspace: запись другого checkout не объявляется
последней попыткой текущего. Отказ не вызывает повторного вступительного
вопроса. Текстовое предупреждение о превышении порогов ограничено одним
разом в сутки; через `maintenance status` оно доступно без ограничений.

При выключенном, отсутствующем или недоступном `systemd --user` состояние
не маскируется под включённое. Если таймер уже принадлежит другому checkout,
команда `enable` не переназначает его: сначала необходимо явно отключить
старую установку. Для `enable` нужен бинарник
`anki-repository-maintenance` рядом с `anki-repo` либо в `PATH`;
обычная сборка `cargo build --release --workspace` создаёт оба бинарника
рядом. Сам `anki-repo` в качестве установленного GC-бинарника не используется.

После применения очистки сохраняется последняя попытка, включая ошибки и
частичную инвентаризацию. При существенном сбое GC пытается передать
необязательное уведомление: в обычном Linux — через D-Bus и `notify-send`,
в WSL2 — в нативный центр уведомлений Windows через `powershell.exe` и уже
установленный у пользователя Windows модуль `BurntToast`.
Установка модулей в процессе GC **не производится**. В WSL2 сначала ищется
`powershell.exe` в `PATH`, затем под `[automount] root` из `/etc/wsl.conf`
(по умолчанию `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`).
При недоступном Windows interop, отсутствии BurntToast, графической сессии
или отказе доставки очистка не прерывается; результат доступен через журнал
systemd, `maintenance status` и snapshot. Полученный от обработчика код 0
не доказывает, что всплывающее окно пользователь действительно увидел.

Одноразовая проверка отправки **без запуска очистки**:

```bash
anki-repository-maintenance notify-test
```

Отдельно для проверки именно контекста пользовательского systemd запускайте
собранный бинарник в одноразовом user-unit. Пример из корня рабочего
пространства после `cargo build --locked -p repository-maintenance`:

```bash
systemd-run --user --wait --collect --pipe \
  "$(pwd)/target/debug/anki-repository-maintenance" notify-test
```

При `CARGO_TARGET_DIR`, заданном пользователем, путь к бинарнику требуется
уточнить по фактической конфигурации сборки. Команда не активирует GC,
не удаляет данные, не устанавливает таймер и не меняет конфигурацию systemd.
В пользовательских службах WSL переменная `WSL_INTEROP` может отсутствовать:
для распознавания платформы она не обязательна, но возможность запуска
Windows-процессов из user-unit проверяется только настоящим тестом.
Доставка Toast зависит от политики уведомлений Windows и доступности
пользовательского сеанса; автоматический запуск Dunst для WSL не нужен.

Это не служба слежения и не отдельная БД.

## Команды

Соберите бинарник из корня рабочей области. Для ручного запуска `clean --apply`
используйте расположение вне очищаемого каталога сборки: собственный процесс
проверяется по PID и времени запуска и не блокирует очистку, но `cargo clean`
удалит файл бинарника, если он находится внутри очищаемого `target`. Пример
собирает бинарник в отдельный каталог:

```bash
MANUAL_BUILD_ROOT="${XDG_CACHE_HOME:-$HOME/.cache}/repository-maintenance-manual-build"
CARGO_TARGET_DIR="$MANUAL_BUILD_ROOT/target" CARGO_BUILD_BUILD_DIR="$MANUAL_BUILD_ROOT/build" cargo build --locked --release -p repository-maintenance
MAINT="$MANUAL_BUILD_ROOT/target/release/anki-repository-maintenance"
```

Эти переменные заданы только для команды сборки. Если они уже экспортированы в
текущей оболочке, удалите их из окружения запуска, чтобы утилита определила
каталоги рабочей области по Cargo:

```bash
env -u CARGO_TARGET_DIR -u CARGO_BUILD_TARGET_DIR -u CARGO_BUILD_BUILD_DIR "$MAINT" clean --apply --json
```

Инвентаризация без записи и стабильный JSON:

```bash
"$MAINT" scan
"$MAINT" scan --json
"$MAINT" scan --detail --json
```

План очистки и явное применение:

```bash
"$MAINT" clean --json
"$MAINT" clean --apply --json
"$MAINT" clean --cleanup-legacy --json
"$MAINT" clean --cleanup-legacy --apply --json
```

`clean` без `--apply` — режим `dry-run`: отчёт показывает планируемое действие по
измеренному каталогу `target` и не запускает очистку Cargo. Это сохраняет строгую
беззаписность: `cargo clean --dry-run` сам создаёт `.rustc_info.json` в target.
Распознанные старые каталоги без маркера владельца по умолчанию сохраняются и
отмечаются как `ownership: unknown`. Флаг `--cleanup-legacy` включает их в план,
а удалить их можно только сочетанием `--cleanup-legacy --apply`. Пользовательский
systemd timer эту опцию не передаёт.
При применении используется обычный `cargo clean` с точно найденными путями.
`clean --apply` неблокирующе захватывает общую блокировку обслуживания и
непосредственно перед очисткой повторно проверяет размер, inode, точки
монтирования и ошибки инвентаризации, маркер владения и процессы. Если блокировка
уже занята управляемой сборкой или другой очисткой, команда сразу завершается с
ошибкой, не дожидаясь её освобождения.
Каталог блокировки расположен в `<XDG_CACHE_HOME>/anki-decks/maintenance-lock`
или `~/.cache/anki-decks/maintenance-lock`, вне дерева внешних сборочных кэшей;
для `clean --apply` должен быть задан `XDG_CACHE_HOME` или `HOME`.
Если повторное измерение показывает размер ниже жёсткого предела, очистка не
запускается. Повторный запуск при отсутствии `target` показывает 0 освобождённых
байт.

Создание и использование внешнего повторно используемого кэша:

```bash
"$MAINT" cache init --id local-check
"$MAINT" cache run --id local-check -- cargo test --workspace --locked
"$MAINT" cache run --id local-check --json -- cargo test --workspace --locked
```

`cache run` принимает прямой вызов Cargo; оболочки и обёртки `env` не
поддерживаются. Допускается указать исполняемый файл с именем `cargo`, включая
`cargo +stable`. Разрешены только встроенные команды сборки `build`, `check`,
`test`, `bench`, `doc` и `run`; Cargo-псевдонимы и внешние команды отклоняются,
чтобы их конфигурация не могла добавить скрытое перенаправление сборки.
Команда запрещает `--target-dir` и `--target-dir=...`, а также
`-C`, который меняет текущий каталог и поиск конфигурации Cargo. Параметр
`--config` запрещён, если значение или TOML-файл меняет `build.target-dir` либо
`build.build-dir`; остальные
параметры разрешённых команд доступны. Параметры после Cargo-разделителя `--`
передаются запускаемой программе и не анализируются как настройки Cargo. Команда
устанавливает оба каталога сборки на зарегистрированный `target` через окружение
и добавляет последние значения конфигурации Cargo после параметров пользователя;
поэтому даже вложенные `include`-файлы не перенаправляют сборку из управляемого
каталога.

До запуска дочерней команды `cache run` проверяет маркер кэша и обновляет время
последнего использования. После завершения Cargo маркер обновляется повторно.
На всём протяжении дочернего процесса удерживается та же эксклюзивная
блокировка обслуживания, что и `clean --apply`. Эти команды сразу завершаются,
если блокировка уже занята: новая команда возвращает ошибку и код 2 без ожидания.
Поэтому `clean --apply` не начинает очистку, пока активен
управляемый `cache run`.

При `--json` stdout обёртки содержит ровно один JSON-документ. Stdout дочернего
Cargo потоково перенаправляется в stderr, а его stderr остаётся в stderr; вывод
сборки не накапливается в памяти. Вне JSON-режима потоки Cargo наследуются
обычным образом. Для запущенного Cargo поле `exit_code` и код возврата обёртки
сохраняют код Cargo; если Cargo завершён сигналом, возвращается `128 + номер
сигнала`. Ошибки проверки, запуска или ожидания Cargo, а также ошибка обновления
маркера после успешного Cargo дают код 2. Если Cargo завершился с ненулевым кодом,
обёртка возвращает его код.

Кэш становится кандидатом сборщика мусора только при превышении общего жёсткого
предела и после истечения семидневного возраста.

Ежедневный пользовательский таймер systemd, который устанавливается по желанию:

```bash
"$MAINT" timer install
"$MAINT" timer status
"$MAINT" timer uninstall
```

Установщик находит исполняемый Cargo в `PATH` текущего процесса установки,
проверяет его командой `cargo --version` и помещает найденный каталог в начало
`PATH` службы, затем добавляет стандартные системные каталоги. Поэтому служба
не зависит от `PATH` интерактивной оболочки пользователя. Установщик копирует
исполняемый файл в `~/.local/bin`, пишет unit-файлы с `%h` вместо
пути конкретной машины и сохраняет корень рабочей области в пользовательской
конфигурации установки. Таймер запускает `clean --apply` один раз в сутки; это
единственный автоматический путь применения изменений. `timer uninstall`
выключает таймер и удаляет только свои unit-файлы, конфигурацию установки и
бинарник. Если пользовательский менеджер systemd недоступен, ручные команды
продолжают работать.

Все режимы поддерживают `--workspace-root`; `XDG_CACHE_HOME`, `--policy` и
`--temp-root` позволяют изолировать кэш, пороги и сборщик `TempWorkspace` в
тестовой среде. `--temp-root` задаёт корень очистки временных каталогов проекта
и каталог для инвентаризации. Отдельно сканируется `std::env::temp_dir()`, только
если его канонический путь отличается от `--temp-root`.

Успешный отчёт возвращает код 0, если `fatal_errors` равен нулю, и код 1, если
есть фатальные ошибки операций обслуживания. В `errors` входят как фатальные
ошибки, так и ошибки инвентаризации временных каталогов. Для записи
`std::env::temp_dir()` поле
`complete: false` обозначает неполную инвентаризацию; поле `errors` считает
ошибки чтения, а границы точек монтирования показаны отдельно. Неполная инвентаризация и её
ошибки не увеличивают `fatal_errors`; если других фатальных ошибок нет, команда
возвращает код 0.
Ошибки, из-за которых отчёт не удалось построить, возвращают код 2; при `--json`
stdout содержит JSON-объект с полями `schema_version` и `error`.
CLI использует `run_and_record`: очистка, повторные замеры и запись последней
попытки выполняются под одной общей блокировкой. Последней считается последняя
завершённая попытка, допущенная к GC этой блокировкой; отказ конкурента получить
блокировку не перезаписывает её snapshot. Блокировка снимается до уведомления. Отсрочка из-за занятой блокировки
(`RunFailure::Deferred`) не вызывает уведомление о сбое; другие ошибки получения
блокировки и выполнения (`RunFailure::Failed`) остаются ошибками. В JSON ошибка
по прежнему представлена строкой, код завершения отказа остаётся 2.
Публичные `run`, `record_report`, `record_failure` сохранены; раздельные вызовы
не обеспечивают эту атомарность, для неё нужен `run_and_record`.
Сбой записи последнего результата `clean --apply` не меняет код возврата: очистка
уже выполнена, а неудача видна в stderr и в журнале таймера. `maintenance status`
в этом случае показывает прежний сохранённый результат, а не текущий прогон.
Неполное измерение Cargo `target` или его `build-dir` (ошибки чтения либо
вложенные точки монтирования) считается фатальной ошибкой при любом видимом
размере: неполные данные не доказывают, что жёсткий предел не превышен.

## `busy`, `deferred` и ограничения

`busy` означает обнаруженный связанный процесс сборки/тестирования или живого
владельца `TempWorkspace`; для `target` это безопасная отсрочка без фатального
статуса. `deferred` означает, что возраст ещё не истёк или повторная проверка
обнаружила занятый путь. `error` отражает непроверенное владение, неизвестное
состояние связанного процесса, ошибку маркера, чтения или очистки. При превышении
жёсткого предела такие ошибки дают ненулевой статус и запрещают удаление. Ни одна
из этих причин не разрешает продолжить удаление.

Исчезновение процесса при обходе `/proc` (`ENOENT` или `ESRCH` при чтении
идентичности) обрабатывается как отсутствие этого процесса. Ошибки доступа,
ввода-вывода и повреждённые данные сохраняют неизвестное состояние и запрещают
очистку; повторная проверка PID и времени запуска остаётся обязательной.

Проверка процессов использует доступные сведения `/proc`: текущий каталог,
исполняемый файл, идентичность процесса, цепочку родителей и открытые файловые
дескрипторы процессов рабочей области. Между последней проверкой и запуском
`cargo clean` остаётся небольшое окно для процесса Cargo, который не использует
этот инструмент: Cargo не предоставляет блокировку, защищающую весь каталог
`target` от параллельной новой сборки. При обнаружении уже работающего связанного процесса
очистка откладывается; таймер сам не запускает сборку.

Полный обход каждого корня инвентаризации может встретить закрытые каталоги root
или systemd. В отчёте
они получают значения `foreign` или `error`; их содержимое может быть
недоступно, поэтому JSON помечает инвентаризацию как `complete: false` и
увеличивает `errors`. Проект не подменяет системный `systemd-tmpfiles` и не
удаляет неизвестные ZIP со свидетельствами, даже если их имена содержат
`anki-decks`.

Оба необязательных обработчика уведомлений ограничены пятью секундами.
При таймауте дочерний процесс завершается и собирается через `wait`; его потоки
закрыты. Ошибка/таймаут не меняют exit status GC или уже сохранённый snapshot;
`notify-test` возвращает диагностируемую ошибку. Windows Toast сохраняет
PowerShell/BurntToast: сначала ищется `powershell.exe` в `PATH`, затем под
`[automount] root` из `/etc/wsl.conf` (по умолчанию `/mnt/c/Windows/...`).
Для другого диска Windows или отключённого automount задайте `PATH` службы.
Код 0 обработчика подтверждает приём запроса, видимость окна проверяется отдельно.
